## 120.16 — Website + cloud deployment posture

Scope: the website deployment tooling and runtime config (`toke-website`: the compiled ooke server, `ooke.toml`, `Makefile`, `scripts/deploy.sh`, `certs/`, `main.tk`) and the private cloud stack (`toke-cloud`: CDK infra, Lambda handlers, Fargate sandbox, Dockerfile). Method: static review of deploy scripts, TLS/ACME wiring, exposed ports/services, secret storage, patch/build posture, and access controls. No builds or long-running commands were executed; findings are grounded in file reads only. This report is stored in the PUBLIC toke repo, so infrastructure is referred to indirectly; concrete host/IP/key specifics live in the private note `toke-cloud/docs/deployment-audit-notes.md`.

The cloud (`toke-cloud`) side is, on the whole, well hardened (isolated VPC, no NAT, dropped capabilities, WAF, minimal IAM — see Positive observations). The findings below concentrate on the self-managed website box, whose deploy path is markedly weaker than the CDK-managed cloud services.

---

### DEP-01 — SSH deploy disables host-key verification (StrictHostKeyChecking=no)
- Severity: Medium
- Reachability: local (attacker on the deploy network path)
- File: `toke-website/scripts/deploy.sh:45`

Description: every SSH/rsync invocation uses `SSH_OPTS="-i ${TOKE_DEPLOY_KEY} -o StrictHostKeyChecking=no -o BatchMode=yes"`. Host keys are never pinned or verified, and the deploy pushes highly sensitive material over this channel: the TLS private key (`rsync certs/`), LLVM IR + C sources, and a remote `clang` compile-and-restart command.

Impact: an attacker able to intercept or redirect the deployer's network path (rogue DHCP/DNS, ARP/BGP hijack, malicious hop) can impersonate the target on first or subsequent connect, capture the pushed TLS private key, and feed attacker-controlled IR/stdlib into the remote `clang` build that then runs as the site process. StrictHostKeyChecking=no removes the trust-on-first-use protection entirely.

Recommended fix: pin the server host key (`known_hosts` / `StrictHostKeyChecking=yes` or `accept-new` seeded once), and keep `BatchMode=yes` for automation. Store the expected host key fingerprint in the private ops notes.

### DEP-02 — Production TLS is a self-signed certificate with no ACME / auto-renewal
- Severity: Medium
- Reachability: remote-unauth
- File: `toke-website/Makefile` (`certs/cert.pem certs/key.pem` target), `toke-website/main.tk:37`

Description: the TLS material served by `http.servevhoststls(port;"certs/cert.pem";"certs/key.pem")` is generated by the `Makefile` target `openssl req -x509 -newkey rsa:2048 -nodes -days 365 -subj "/…/CN=tokelang.dev"`. The deployed `certs/cert.pem` confirms this: subject == issuer (self-signed), validity Apr 2026 → Apr 2027. There is no ACME/Let's Encrypt/certbot integration anywhere in the repo, and no systemd timer or renewal hook.

Impact: (1) The certificate must be manually regenerated and redeployed every 365 days — a missed renewal is a hard outage. (2) A self-signed origin certificate cannot be authenticated by the fronting CDN in strict mode, so the CDN-to-origin hop is encrypted but not authenticated (origin-impersonation risk if that hop is intercepted). (3) `-nodes` means the private key is unencrypted at rest.

Recommended fix: adopt an automatically renewing origin certificate — either the CDN provider's long-lived origin cert with strict origin validation, or ACME with an auto-renew timer. Alarm on certificate expiry (e.g. < 21 days remaining).

### DEP-03 — Unencrypted TLS private key distributed by rsync and kept in the working tree
- Severity: Medium
- Reachability: local
- File: `toke-website/scripts/deploy.sh:140-146`

Description: `rsync_content()` copies the entire `certs/` directory (including the unencrypted `key.pem`, see DEP-02) from the developer's working copy to the server on every content and full deploy. The private key therefore lives, unencrypted, both in the developer machine's checkout and on the server, and is re-transmitted routinely.

Impact: the origin private key's exposure surface is the union of every machine that has ever run a deploy plus the server. Compromise of the developer laptop (or any interception of the deploy channel — see DEP-01) yields the live origin key, allowing decryption/impersonation of origin TLS. `certs/` is correctly `.gitignore`d (good — it is not committed), but distribution-by-rsync still spreads the secret.

Recommended fix: provision the origin key directly on the server (or via a secrets manager) and never rsync it from a workstation; rotate the key given it has been transported this way. If the CDN terminates TLS, keep the origin key on the box only.

### DEP-04 — No process supervision: server launched with pkill + nohup, no restart-on-crash/reboot
- Severity: Low
- Reachability: n/a (availability)
- File: `toke-website/scripts/deploy.sh:219-229`

Description: the full deploy restarts the site with `pkill -f website_server || true; sleep 1; nohup ./website_server > logs/server.out 2>&1 &`. There is no systemd unit, supervisor, or resource limit — the site runs as an orphaned background job. No `*.service`/`*.timer` files exist in the repo.

Impact: a crash or an instance reboot leaves the site down with no automatic recovery; there is no restart backoff, no journald capture, no cgroup/memory limit, and the `pkill -f website_server` pattern can match unintended processes. This also undermines the availability guarantees of the TLS/renewal story above.

Recommended fix: run the server under systemd (with `Restart=on-failure`, resource limits, and `WantedBy=multi-user.target` so it survives reboot), or an equivalent supervisor.

### DEP-05 — Compiler toolchain and C sources shipped to and compiled on the production host
- Severity: Low
- Reachability: local
- File: `toke-website/scripts/deploy.sh:190-217`

Description: full deploy rsyncs `main.ll` plus the entire stdlib C source tree to the server and runs `clang-15 main.ll stdlib/*.c -o website_server …` on the production box. The build happens on the internet-facing host, as the deploy user, from inputs pushed over the DEP-01 channel.

Impact: keeping a full C/LLVM toolchain on the production host enlarges the attack surface (useful to an attacker for on-box compilation) and makes the running binary a function of remotely-supplied, unverified build inputs. A tampered `main.ll` or stdlib source (e.g. via DEP-01) is compiled and executed as the site process.

Recommended fix: build the binary in CI or on a build host, verify/checksum the artifact, and ship only the finished binary to production. Remove the compiler from the runtime host.

### DEP-06 — Live infrastructure IP and SSH key path hardcoded in deploy-script comments
- Severity: Low
- Reachability: build-time (information disclosure if repo is public)
- File: `toke-website/scripts/deploy.sh:27-29`

Description: the usage comments embed a concrete server IP address and the SSH private-key filename as `export` examples. The website repo's origin is a GitHub remote; if that repo is or becomes public, these comments disclose infrastructure topology and the key-naming convention. (Specifics recorded privately, not repeated here per the public-repo rule.)

Impact: leaks target host and key-file naming to anyone who can read the repo — reconnaissance aid. Even though the referenced address appears to be a decommissioned host, the pattern is a standing hygiene problem and violates the project's "no IPs/infra in public docs" rule.

Recommended fix: replace concrete values in comments with placeholders (`TOKE_DEPLOY_HOST=<host>`, `TOKE_DEPLOY_KEY=<path-to-key>`); keep real values only in a private, untracked env file.

### DEP-07 — API keys stored in cleartext as the DynamoDB partition key (cross-reference)
- Severity: Medium
- Reachability: remote-auth (requires table read access)
- File: `toke-cloud/lambda/api-gateway/toke_api_lambda.py:196-202`, `toke-cloud/infra/lib/toke-cloud-stack.ts:135-142`

Description: the API-gateway Lambda validates keys via `keys_table.get_item(Key={"api_key": api_key})`, and the CDK table definition uses `api_key` (attribute type `S`) as the raw `HASH` key. The presented bearer token is therefore stored verbatim as the primary key of `toke-apikeys`. (Usage/feedback records in the same handler correctly store only a SHA-256 prefix — the lookup table does not.)

Impact: any read access to the key table (misconfig, snapshot/backup exposure, over-broad IAM) yields directly usable, un-hashed API keys. Hashing at rest would render a table dump non-replayable.

Recommended fix: store `sha256(key)` as the partition key and hash the presented token before lookup; migrate existing keys. Note: this overlaps the crypto/secrets and database audit stories — flagged here only because "secret storage" is in this story's scope.

### Dynamic-testing follow-up
- Confirm at runtime which port/mode the production site actually listens on: `main.tk` defaults to port 443 + TLS, `ooke.toml` declares `port = 8081`, and `deploy.sh`'s health check curls `http://localhost:8081/health` while the full-deploy start command passes no flags (would bind 443 + TLS). This configuration drift should be resolved and the effective privilege level of the listener (root vs `CAP_NET_BIND_SERVICE` vs CDN-fronted 8081) verified on the box.
- Verify the fronting CDN's origin TLS mode (strict vs full) against DEP-02 to quantify the origin-impersonation exposure.
- Confirm the OS patch/update cadence on the website instance (unattended-upgrades or equivalent) — not observable from the repo.
- Confirm whether a backup/snapshot schedule exists for the website box and its flat-file store (`ooke.toml` `store.backend = "flat"`); no backup tooling is present in-repo.

### Positive observations
- `toke-cloud` Lambda/Fargate posture is strong: isolated VPC with `natGateways: 0`, security groups with no inbound and `allowAllOutbound: false`, and the sandbox drops ALL Linux capabilities, uses a read-only root filesystem, non-root uid 1000, `no-new-privileges`, a seccomp profile, a 16 MiB tmpfs, and fresh-task-per-execution (`infra/lib/fargate-sandbox.ts`, `infra/lib/toke-cloud-stack.ts:58-76`).
- WAF is enforced in **block** mode with a per-IP rate-limit rule plus AWS managed rule groups (`infra/lib/waf-rules.ts:45-102`); CloudFront enforces `HTTPS_ONLY` viewer/origin protocol and `TLS_V1_2_2021` minimum (`toke-cloud-stack.ts:471-490`).
- CloudFront access logs go to an S3 bucket with `BlockPublicAccess.BLOCK_ALL`, S3-managed encryption, and a 90-day lifecycle (`toke-cloud-stack.ts:423-436`).
- IAM for the tkc Lambdas is minimal (CloudWatch Logs only) and DynamoDB tables use `RemovalPolicy.RETAIN` to prevent accidental deletion (`toke-cloud-stack.ts:89-105,133,143,157`).
- Secret hygiene in `toke-cloud`: `.gitignore` excludes `.env*`, `*.pem`, `*.key`, and `secrets/`; a `.gitleaks.toml` is present; and the website repo `.gitignore` excludes `certs/`, so the TLS private key is not committed.
- Usage and feedback records hash the API key (`sha256` prefix) rather than storing it raw (`toke_api_lambda.py:341,518,529`).
