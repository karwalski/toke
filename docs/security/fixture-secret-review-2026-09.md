## Classification key

| Class | Meaning |
|-------|---------|
| **(a)** | Synthetic test fixture, safe to publish — obviously fake, or a published tutorial constant, or a scanner false positive on source identifiers |
| **(b)** | Synthetic but scanner-tripping — plausible enough to keep tripping scanners; replaced with an unmistakably fake value |
| **(c)** | Possible real credential — could authenticate to a real service; **not touched**, owner ratification required |

## Verification method

Claims were checked, not assumed:

- **JWT hits** — header and payload decoded; signatures tested against the
  published tutorial secrets. Every HS256 hit that decodes to the well-known
  demo claim set verifies under the *publicly documented* jwt.io demo secret,
  which proves it is the tutorial token rather than a token issued by any real
  system. The remaining tokens were produced by the reference programs at
  test-run time and carry only example claims (reserved `example.com`
  addresses, `admin`, numeric placeholder subjects) — no real issuer or audience.
- **`private-key` hits** — each PEM block was fed to `openssl rsa -check` to
  separate genuine key material from marker-only placeholders.
- **`generic-api-key` hits** — inspected in context. Most are entropy false
  positives on toke source identifiers, compiler diagnostic JSON (temp file
  paths), or hex/base64 crypto values that the test programs themselves
  computed at run time.
- **Reachability** — for every history hit, whether its commit is an ancestor
  of the pushable refs, and whether the file is already present on `origin`.

## (b) remediation

Two hits, both the same ephemeral key, both in `results/python-refs/messaging/MSG-003/`.

**What it was:** the RSA keygen task (MSG-003) expects a literal `...` PEM
template, which no correct program can emit; the Python reference solution
therefore generated a real 2048-bit keypair at test-run time and was recorded
as `WRONG_OUTPUT`. The recorded output was a complete, valid private key —
confirmed by `openssl rsa -check`. It was never provisioned to any service and
authenticates nothing, but it is genuine key material and would have kept every
future scan of a public repo red.

**What changed:** the base64 key body in `output.txt` and in the `actual` field
of `status.json` was replaced with the literal placeholder
`REDACTED-SYNTHETIC-EPHEMERAL-KEY-BODY-REMOVED-BY-STORY-130.20`, keeping the
surrounding PEM markers so the record still shows *what kind* of output the
reference produced. The `status` (`WRONG_OUTPUT`) and `expected` fields are
untouched, so the failure record and every count derived from it are unchanged.
No other file in either repo contains that key body.

**Verification:**

- `openssl rsa -check` on the file now fails — no parseable key material remains.
- Every remaining `private-key` hit in the repo was re-checked and confirmed
  **marker-only**: no base64 body in any of them.
- `infra/corpus-summary.py` reproduces the same corpus table (2,065 programs;
  Python `WRONG_OUTPUT` 327).
- The library harness (`scripts/test-library-1460.py`) reads only
  `results/library/*.json` and `results/solutions/`; MSG-003 is in neither, so
  the changed files are outside its input set. A scoped re-run of its logic over
  the messaging category (the category containing the change) is green:
  **110/110 PASS**, 0 failures of any kind.
- `toke-website` needed no (b) changes; its tree is unmodified. `make check-docs`
  passes clean.

**Note on hit counts:** the working-tree count moves 40 → 41, not down. The
`private-key` rule matches on the `-----BEGIN/END-----` markers alone, and the
reformatted `status.json` now presents two marker pairs where the old
single-line blob presented one. This is cosmetic. The security-relevant
measure is that **zero real key material remains in either working tree**.

### 2. `toke-test-programs/categories/security/requirements.yaml` line 1117, commit `bbfca8d6` (2026-05-24) — `stripe-access-token`

**Not touched.** This is the one hit that could name a real service.

- **Service it appears to target:** Stripe. The value carries the live secret
  API key prefix (`sk_live_`-class), which is why the Stripe rule fired.
- **Evidence it is synthetic:** it sits in the `test_cases` block of an API-key
  strength-analyser requirement, as the input whose `expected_output` is
  `"strong"`; the immediately preceding case is a deliberately weak
  `key-12345678` → `"weak"`. Its length does not match either Stripe live-key
  format. No Stripe SDK, client, or credential consumer exists anywhere in
  `toke`, `toke-website` or `toke-test-programs` — the only other occurrences of
  the word are a fixture tool name in an ai-agents test program.
- **Exposure:** minimal and **not on the push path**. The value is absent from
  both working trees, from `HEAD`, from `main`, and from both `origin` refs. It
  survives only in `refs/original/refs/heads/main`, a leftover `git
  filter-branch` backup ref in the local clone. `git push` never sends
  `refs/original`, so neither pending push can publish it. `git gc --prune`
  after deleting that ref removes it locally.
- **If the owner confirms it was a real key, rotation would involve:** Stripe
  Dashboard → Developers → API keys → roll the live secret key; update any
  consumer of it (none known in these repos); review Stripe's API request logs
  for use of the old key; then strip the blob under story 130.15. **None of
  this was done** — the owner ratifies first.

**Recommended owner check (one question):** was a Stripe account ever
provisioned for this project? If no — which the absence of any integration
strongly suggests — the finding closes as (b)-historical with no action beyond
deleting the stale `refs/original` ref.
