The `pkg.toml` file is the package manifest for toke projects. It declares the project identity and its external dependencies. This document is the normative reference for the TOML schema; see also Section 24.3 of the toke specification.

## Location

`pkg.toml` MUST be placed at the project root directory (the same directory from which `tkc` is invoked). Projects with no external dependencies MAY omit the file entirely.

---

## Schema

### `[package]` table (required)

| Field     | Type   | Required | Description |
|-----------|--------|----------|-------------|
| `name`    | string | yes      | Package name. Lowercase ASCII letters and digits only (`[a-z][a-z0-9]{0,62}`). No underscores, hyphens, or dots. `std`, `pkg`, `toke` and `tkc` are reserved. |
| `version` | string | yes      | SemVer 2.0 version (`MAJOR.MINOR.PATCH`, no leading zeros). Pre-release (`-rc.1`) and build (`+sha.5114f85`) suffixes are permitted — checked against the SemVer 2.0 grammar — but ignored during dependency resolution. |

**Example:**

```toml
[package]
name = "myapp"
version = "1.0.0"
```

### `[dependencies]` table (optional)

Each key is a package name; each value is a version constraint string.

**Simple form — version constraint as string value:**

```toml
[dependencies]
webframework = ">=0.3.0"
jsonparser = "1.2.0"
utils = ">=2.0.0 <3.0.0"
```

**Extended form — table with version and git URL:**

```toml
[dependencies.webframework]
version = ">=0.3.0"
git = "https://github.com/example/toke-webframework.git"
```

The `git` field is optional. When omitted, the compiler resolves the package name via the central index (when available) or emits E9011. When present it must be an authenticated transport: `https://host/path`, `ssh://[user@]host/path` or `[user@]host:path`. `http://`, `git://`, `file://`, local paths, git's `ext::`-style helpers, anything beginning with `-`, and a user or password inside an https URL are refused (ADR-0004, "Supply-chain security").

**No other tables or keys.** The schema is closed: a table other than `[package]`, `[dependencies]` and `[dependencies.<name>]`, a key other than the ones listed above, or a line that is not `key = "value"` is an error. In particular a package cannot declare build scripts or install hooks — there is nowhere to put one (story 121.39).

## Version Constraint Syntax

| Form                    | Meaning |
|-------------------------|---------|
| `"1.2.0"`              | Exactly version 1.2.0. |
| `">=1.2.0"`            | Version 1.2.0 or any later version. |
| `">=1.2.0 <2.0.0"`    | At least 1.2.0, strictly less than 2.0.0. |

Versions in a constraint are releases: a pre-release or build suffix in a constraint produces E9012, and so does anything after the version other than the `<` bound — an upper bound not above the lower bound (`">=2.0.0 <2.0.0"`) included. Tilde (`~`), caret (`^`), and wildcard (`*`) ranges are reserved for future versions and SHALL produce E9012 if used.

Resolution takes, for each package, the highest minimum any constraint names (minimal version selection, ADR-0004) and then checks it against every constraint on that package: if it is not an exact version one of them names, or reaches an upper bound, no version satisfies the graph and resolution fails (E9025). Until story 121.46 the upper bound was never read — `">=1.2.0 <2.0.0"` meant `">=1.2.0"` — and an exact version acted as a minimum.

## Complete Example

```toml
[package]
name = "webapp"
version = "0.1.0"

[dependencies]
webframework = ">=0.3.0"
jsonparser = "1.2.0"
templates = ">=1.0.0 <2.0.0"

[dependencies.authlib]
version = ">=0.5.0"
git = "https://github.com/example/toke-authlib.git"
```

This declares a project named `webapp` at version `0.1.0` with four dependencies. Three use the simple constraint form (resolved via the central index); one uses the extended form with an explicit git URL.

## Lock File (`pkg.lock`)

After running `tkc pkg resolve`, the compiler writes `pkg.lock` alongside `pkg.toml`. Format 2 (story 122.10; the design is ADR-0004, "Supply-chain security") records, for every dependency, the resolved version, the source it was fetched from (story 121.39), the full git commit id and a content hash:

```toml
# pkg.lock — auto-generated by tkc pkg resolve
# Do not edit manually.
lock-version = "2"

[resolved]
webframework = "0.3.0"
jsonparser = "1.2.0"

[source]
webframework = "https://github.com/example/toke-webframework.git"
jsonparser = "git@github.com:example/jsonparser.git"

[commit]
webframework = "a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2"
jsonparser = "f6e5d4c3b2a1f6e5d4c3b2a1f6e5d4c3b2a1f6e5"

[hash]
webframework = "sha256:<64 lower-case hex digits>"
jsonparser = "sha256:<64 lower-case hex digits>"
```

- A **commit** is exactly 40 (SHA-1) or 64 (SHA-256) lower-case hex digits. Branch names, tag names and abbreviated ids are rejected, because they can move.
- A **hash** is `sha256:` and 64 lower-case hex digits over the package's canonical tree, defined in ADR-0004.
- A **source** follows the same transport rule as the manifest's `git` field. It is recorded once, so a later fetch never asks the index again.
- `[source]`, `[commit]` and `[hash]` entries must name a package listed in `[resolved]`. Any other table, or a malformed line, makes the lock unreadable.
- A lock written by `tkc pkg resolve` before any fetch has versions only. **Fetching or building against a lock in which any dependency lacks a source, a commit or a hash is an error**, and so is a fetched package whose commit or content hash differs from the lock. The content hash is computed from the fetched files by the verifier itself.
- A lock with no `lock-version` line (written before 122.10) is read as format 1: versions only, nothing pinned.

`pkg.lock` SHOULD be committed to version control. It is what makes a build reproducible and what stops a moved tag or a tampered download from being built.

> **Status.** The lock format, its validation, the source policy, the content-hash computation and the pin/verify checks are implemented in `src/pkg.c` and tested (`test/conform/C140_pkg_lock_pins.sh`, `test/conform/C492_pkg_integrity_by_construction.sh`). `tkc pkg fetch` itself does not exist yet: `src/pkg.c` is network-free and not linked into `tkc`. An earlier revision of this page showed a `[package.<name>]` table layout that no code ever read or wrote.

## Validation Rules

1. The `name` field MUST match `[a-z][a-z0-9]{0,62}` and MUST NOT be a reserved name (`std`, `pkg`, `toke`, `tkc`).
2. The `version` field MUST be valid SemVer 2.0.
3. Dependency names MUST match the same naming rule as `name`.
4. Version constraint strings MUST use one of the three supported forms.
5. If the extended form is used, the `version` field is required; `git` is optional and must be an https or ssh source.
6. Duplicate dependency names produce E9012, including one name declared in both forms.
7. Unknown tables, unknown keys and lines that are not `key = "value"` produce E9012.

## Diagnostics

| Code  | Condition |
|-------|-----------|
| E9025 | No version of a dependency satisfies all constraints in the transitive graph. |
| E9011 | Package name not found in the central index and no `git` URL specified. |
| E9012 | Malformed `pkg.toml`: missing required field, invalid TOML, or unsupported constraint syntax. |
| E9013 | Git clone/fetch failed for a dependency repository. |
| E9014 | No git tag matches the resolved version for a dependency. |
| W9010 | `pkg.lock` is out of date relative to `pkg.toml`. |

These codes are reserved in the compiler's code registry (`src/pkg.h`,
`docs/reference/errors.md`) but not yet emitted: the resolver is not wired
into a `tkc` command. Until story 121.50 the unsatisfiable-constraints
condition was documented here as E9010, a code the compiler already uses for
"compiler limit exceeded"; codes are stable, so it moved to E9025, the next
free code at the end of the E9xxx series (story 121.50; E9024 is the
compiler's, 121.28).
