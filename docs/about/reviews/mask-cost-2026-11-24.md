> **A measurement record, not a published claim.** None of these numbers is in
> `docs/metrics-baseline.md`, and none may be quoted anywhere else until the owner puts
> one there. Each figure below is wall time on one machine. Every one of them comes with
> its metric type, engine, tokenizer, baseline and N.

The 2026-11-23 record (`docs/about/reviews/mask-cost-2026-11-23.md`, story 131.52) found
that toke's character-level grammars are expensive to mask with: tens of milliseconds
per token in XGrammar, and llguidance refuses them under its default limits. It named
the test that would be fair to toke: grammars written for each engine, for toke and for
the Python baseline alike. This record is that test (story 131.141).

## What was built

Four new grammars. Each one is generated by a script from a grammar that is already
gated, so none can be edited by hand without a gate failing.

| File | Engine | Generated from | Form |
|---|---|---|---|
| `docs/spec/toke-lexeme.lark` | llguidance | `docs/spec/toke.gbnf` by `scripts/gbnf_tune.py` | lexical rules as regex lexemes, multi-character terminals |
| `docs/spec/toke-xgr.gbnf` | XGrammar | `docs/spec/toke.gbnf` by `scripts/gbnf_tune.py` | whitespace inlined, word-end lookahead assertions |
| `bench/mask_cost/python-subset-lexeme.lark` | llguidance | `python-subset.gbnf` by `python_subset_gbnf.py` | as for toke |
| `bench/mask_cost/python-subset-xgr.gbnf` | XGrammar | `python-subset.gbnf` by `python_subset_gbnf.py` | as for toke |

- **The lexeme form** keeps the parser rules of the source grammar. Identifiers,
  numbers, strings, comments and whitespace runs become regex lexemes. Whitespace is two
  lexemes, spaces and comments, because llguidance's lexer never backtracks: with a
  single whitespace lexeme, ` (` is lexed as the start of a comment and then fails. That
  first draft disagreed with the reference on 4 fragments. A regular expression cannot
  nest, so toke's nested comments and string interpolation are unrolled to 8 levels.
  `toke-lexeme.lark` therefore accepts a **subset** of the language of `toke.gbnf`: it
  rejects nesting deeper than 8, which the parser accepts. The deepest nesting in the
  fragment set is 2 for comments and 3 for interpolation.
- **The XGrammar form** describes the same language as its source. Every `ws` / `ws1`
  reference is inlined as a character-class loop. The rules that end a word token
  (identifiers, numbers, scalar type names) carry the assertion `(= [^a-zA-Z0-9])`.
  In XGrammar 0.2.9 the assertion is only a hint for its mask cache. A deliberately wrong
  assertion changed no mask, so the assertions are not shown to have any effect here.
- `toke.gbnf` and `grammar.ebnf` are unchanged, so the published production count is
  unchanged.

### The gates

- **toke.** `make check-grammar-artefacts` (run by `make ci`) runs
  `scripts/gbnf_tune.py --check`. It fails if either file differs from a fresh
  generation from `toke.gbnf`. Where the engines are installed, it also runs llguidance
  on `toke-lexeme.lark` and XGrammar on `toke-xgr.gbnf` over every fragment of
  `test/gbnf/fragments.json`, against the reference recogniser (`gbnf_earley` on
  `toke.gbnf`, which `make check-gbnf` ties to the parser). Both agree on 2081 of 2081
  fragments (1135 accepted, 946 rejected).
- **Python subset.** `make bench-mask-cost-check` checks that both tuned forms agree with
  `python-subset.gbnf` on 3857 of 3857 inputs: 383 coverage programs, 27 traps and 3447
  single-edit mutants.

**Limits of the gates.**

1. **CI runs the staleness check only.** CI's Python has neither engine installed. There
   the two agreement checks report SKIPPED, never a pass, and only the staleness check
   runs. Staleness shows that a file matches its generator, not that the generator is
   right. So the guarantee that the tuned forms agree with the parser holds only where
   `bench/mask_cost/requirements.txt` is installed. `--require-engines` turns SKIPPED
   into a failure, but nothing passes it yet. The same was already true of `toke.lark`
   (`scripts/gbnf_to_lark.py`).
2. **Agreement is not equivalence.** Agreement is measured on the fragment set. It does
   not prove that the tuned forms describe the language of `toke.gbnf`. Some productions
   are barely exercised. In a review, the `fn` alternative was removed from `ident` in
   both tuned forms, and both still agreed on 2081 of 2081 fragments. Only the staleness
   check caught it. That check stops a hand edit, so only a bug in the generator can get
   past the gates unnoticed.
3. **The lookahead assertions are sampled, not proved.** `gbnf_tune.py --check --tokens`
   fills XGrammar masks over cl100k_base at the tokens of a sample of accepted fragments
   and fails if any mask disallows the fragment's own next token. The 2026-11-24 run with
   stride 16 covered 71 fragments and 11,216 masks, and none disallowed. That guards
   against a future engine that trusts the hint. It does not prove each assertion is
   implied by the grammar.

## Method

The method is the 2026-11-23 method, with one change: compile time is the median of
**3** runs instead of 5, to keep the run bounded. Each XGrammar compile of
`python-subset-xgr.gbnf` takes about 3.6 minutes.

- **Metric 1, mask time.** Wall time of one next-token mask over the whole vocabulary,
  in microseconds. A fresh matcher consumes each program's real tokens, and the mask is
  filled once at each of 16 evenly spaced token positions, end of text included. Each
  pass is cold and runs on one thread. A state is never filled twice.
- **Metric 2, compile time.** Wall time to build the matcher state for the vocabulary,
  in seconds: the median of 3 runs, on one thread, with XGrammar's cache off. For
  llguidance this is a lower bound, because it compiles lazily.
- **Tokenizer.** cl100k_base, through tiktoken 0.14.0: 100,277 ids, with the 16
  unassigned ids padded with strings no grammar matches. The table's sha256 is
  `b18b4eea0bbc2915...`, and the full value is in the JSON.
- **Engines.** XGrammar 0.2.9 and llguidance 1.9.1. llguidance ran twice: once with its
  default limits, and once with `step_max_items` raised from 50,000 to 5,000,000. Each
  engine measured only the forms written for it.
- **Content.** N = 48 programs in three notations, chosen as before. On this commit all
  383 candidate `.tk` files outside `test/` passed every filter, against 376 of 381 on
  2026-11-23. The 48 measured are every 7.98th of the 383 in git order, so the set
  differs from the one measured on 2026-11-23 (paths in the JSON). **Compare figures
  within this record only.**
- **Machine.** Apple M2 Pro (arm64, 12 CPUs), macOS 26.7.1, CPython 3.14.7, as reported
  by `sysctl machdep.cpu.brand_string`. The 2026-11-23 record names an M4 Max. This is a
  second reason not to compare absolute times across the two records.
- **Commit.** toke 76feacf8, the 131.141 branch. The grammar sha256 prefixes are
  `toke-lexeme.lark` 9190a0e5, `toke-xgr.gbnf` fac2bea2, `python-subset-lexeme.lark`
  588496a7 and `python-subset-xgr.gbnf` 849a2f73. The full values are in the JSON.
- **Reproduce.** `make bench-mask-cost GRAMMAR_PY=<venv>/bin/python`, or call
  `bench/mask_cost/mask_cost.py --compile-runs 3` directly, as this run did. The
  measuring took about 19 minutes in total, 11 of them on `python-subset-xgr`. The
  result is written to `build/mask-cost/mask-cost-2026-11-24.json`, which is not
  committed.

## What this says

1. **Writing the grammar for the engine is what makes masking cheap.** The language
   stays the same. With llguidance and raised limits, the median mask falls from 2,920
   µs to 524 µs for toke and from 27,884 µs to 1,495 µs for the Python subset. With
   XGrammar it falls from 35,577 µs to 1,192 µs for toke and from 25,003 µs to 5,392 µs
   for the Python subset. All four use cl100k_base and N = 768 positions from 48
   programs. The JSON control shows the same effect: XGrammar's built-in grammar masks
   in 7.7 µs against 32,908 µs for the textbook GBNF (N = 768).
2. **toke-lexeme.lark is the only grammar here, apart from JSON, that llguidance runs
   under its default limits.** It finished 48 of 48 programs with a median mask of 528
   µs, against a 2,513 µs median for the JSON grammar (cl100k_base, N = 768). The
   character-level toke and Python grammars stop on every program. The tuned Python form
   still stops on 40 of 48. That is a limit of this baseline grammar, probably its
   per-indentation-level rule copies, and not a property of Python. The default-limits
   comparison is therefore not a toke advantage. Fixing the baseline is proposed as a
   follow-up (131.148). **Superseded by the 2026-11-25 addendum below:** the rebuilt
   Python form finishes 48 of 48 under default limits.
3. **Tuned against tuned, toke's mask is cheaper than the Python subset's in both
   engines.** (The llguidance half is revised by the 2026-11-25 addendum below:
   against the rebuilt Python form the medians are 501 µs and 989 µs, llguidance 1.9.1 with
   `step_max_items` 5,000,000, cl100k_base, N = 768 positions from 48 programs.) With llguidance and raised limits, the medians are 524 µs against
   1,495 µs, and toke is lower at p90 and at max too. With XGrammar, the medians are
   1,192 µs against 5,392 µs, but the tails are about equal: p90 48,250 µs against
   43,784 µs, and max 584,488 µs against 616,680 µs. All use cl100k_base and N = 768
   positions from 48 programs each. On 2026-11-23, with the character-level forms, toke
   was the more expensive of the two in XGrammar.
4. **XGrammar's tail and compile time are still a problem.** In the tuned XGrammar forms,
   the worst positions still take about half a second per mask (max 584,488 µs for toke
   and 616,680 µs for Python). Compile time rises a hundredfold for toke, from 0.418 s to
   44.1 s, and is 215.5 s for the Python subset (3 runs each, cl100k_base). The inlining
   enlarges every rule that references whitespace. The tuned form trades compile time
   for a lower median. Whether that trade is worth making is an owner question, not
   settled here.

So the claim "a small grammar makes the mask cheap" now has some support, with
conditions. It holds when both languages get grammars written for the engine, it holds
fully only in llguidance, and it holds in XGrammar only at the median. It does not hold
for the character-level grammars, as the 2026-11-23 record showed.

## Addendum 2026-11-25: the Python baseline under default limits (story 131.148)

Point 2 above left the default-limits comparison unfair. Under llguidance's default
`step_max_items` of 50,000, `python-subset-lexeme.lark` stopped on 40 of the 48 programs.
Story 131.148 rebuilt that one file. The Python subset's language is unchanged.
`python-subset.gbnf` and `python-subset-xgr.gbnf` are byte-identical, and so are the toke
grammars.

### Why it stopped

A mask walks the vocabulary's token trie. Wherever a lexeme ends inside a token, the
engine scans that lexeme and adds an Earley row, and the 50,000 cap counts the items of
all those rows together. The cost is therefore the number of rows times the items per
row. Two things made the rows large:

1. **Every operand position predicted a long list of alternatives.** Each one is a row
   item: six string kinds, three constants, numbers and `...`, the bracket displays and
   six operator levels. Removing one alternative cut about 1,000 to 2,000 items from a
   mask.
2. **Each enclosing indentation level added about 3,000 items.** After every newline
   inside a token, each enclosing level contributed its own items: a `blank*` loop, the
   next statement, and the `elif` / `else` / `except` continuations. A run of blank lines
   added one row per line. This was measured with one `if` level added at a time
   (`x = y` at levels 0 to 6: 43,188 to 61,131 items needed with only the operand fixes).

Neither of the suspected causes was the main one. The per-level statement copies cost
little until a program is nested, and flattening the precedence chain alone moved the
default-limits result from 8 of 48 to 21 of 48.

### What changed

`bench/mask_cost/python_subset_gbnf.py` passes `lexeme_lark` a set of rule rewrites that
accept the same strings, for the llguidance form only:

- `bor` .. `power` become one level, `factor (binop factor)*`, and `or` / `and` become one
  level too. Precedence shapes the parse tree, not the set of strings accepted.
- A choice among fixed strings becomes one regex lexeme: the binary, comparison and
  augmented-assignment operator sets, the four plain string kinds, `None` / `True` /
  `False`, a number or `...`, and `pass` / `break` / `continue`.
- Augmented and annotated assignment share their single-target prefix.
- The blank lines before a line and that line's indentation become one lexeme per level,
  `ind<k> ::= blank* "<4k spaces>"`, and `root` becomes `ind0 (stmt0 ind0)*`.

This needed one generator fix. `scripts/gbnf_tune.py` did not escape `/` inside a Lark
`/regex/`, so a lexeme containing `/` or `//` broke the grammar. Neither existing lexeme
file contains one, so both regenerate byte-identically.

- **Machine and engines.** Same machine, same engines (llguidance 1.9.1), same tokenizer:

- **Programs.** The same 48 programs: the selected paths are identical to the
