# Review: KERN / KERN-py benchmarks against toke

**Subject:** https://oscarcode9.github.io/kern-language.html ("KERN-Py — Token Efficiency Engine & Reversible DSL for LLMs", Oscar Martinez; published 2026-03-03, updated 2026-08-01) and the repository behind it.
**Reviewed:** 2026-09-18, story 133.1. Tone: evidence and open questions only.

## 1. Summary

KERN is a compact, reversible surface syntax for Python (Python → Kern → Python, deterministic round-trip; grammar v0.4; optional `compact=True` profile that alpha-renames locals and applies conservative simplifications). Its semantics, runtime and test suites are Python's. The page benchmarks Kern against Python, python-minifier, Sigil, KARN, NERD, Vyxal and **toke**.

Everything KERN publishes about toke is **reproducible from public artefacts and reproduces exactly** on our machine (tkc 2.8.0): 3,012 vs 6,347 cl100k tokens (Kern is 52.54% below the pinned toke sources), 29/60 of those sources accepted by the current compiler, and 2,788 vs 3,906 in their native-tokenizer lane. Their harness is careful: pinned commits, pinned wheel SHA, full denominators, and explicit "this is not Toke's private held-out test" caveats.

Three findings qualify the numbers rather than dispute them:

1. **The toke side is Gate-1-era output, not current toke.** The 60 toke programs are the April 2026 model-generated solutions in `toke-eval` at commit `851f6d8b` (legacy 80-char syntax: `M=`, `F=`, `[i64]`, `:void`), compiled with `--legacy --check` under tkc 2.8.0 (July 2026). The 29/60 is compiler drift on stale generated code — an artefact on **our** side (the public solutions were never refreshed), which KERN's own report says explicitly. It is not a Pass@1 measurement of any toke model.
2. **The "Toke-16K" lane scores our v0.3 tokenizer on text of a syntax it was not trained on.** `toke-tokenizer==0.1.0` ships `tokenizer_v03.json` (16,384 vocab, trained on *default-syntax* v0.3 source). Applied to the legacy-syntax sources it yields 3,906 tokens; applied to the same programs after `tkc --migrate` + `--min` it yields 2,982 (or 2,872 for the toke-eval HEAD migration). Against Kern-16K's 2,788 the equal-vocab gap shrinks from 28.6% to 3–6%, with a bootstrap 95% CI that includes parity (§6).
3. **The 25,953 is deliberate mirroring, not reuse of our corpus.** Their training manifest requests exactly 25,953 CodeSearchNet Python functions "matching Toke's published program count". No toke data is involved (§4).

The shared-tokenizer result itself (toke ≈ 1.76–1.79× Python on cl100k for these tiny JSON-CLI programs) is consistent with what we already publish in `docs/reference/token-comparison.md` ("toke (cl100k) vs Python (cl100k): −80%"), which KERN cites. There is nothing to correct in their arithmetic.

**Recommendation: respond constructively, and correct our own stale public artefacts** (§8). Do not ignore; do not accuse.

## 4. The 25,953 question (task b)

**Finding: coincidence by design; no toke data involved.**

Evidence (all from `benchmark_results/native-tokenizer/` at `db95a75`):

- `README.md`: "Training: exactly `25,953` valid Kern compact programs from the official `train` partition, **matching Toke's published program count**."
- `kern-16k-training-manifest.json`: `dataset.repository = code-search-net/code_search_net`, `training.split = train`, `training.requested = 25953`, `training.accepted = 25953`, `training.scanned = 27569` (rejections: python_parse 383, roundtrip_ast 1054, transform_or_compile 151, source_too_long 27, duplicate_kern 1), `accepted_repositories = 1022`, aggregate sha256 of the Python and Kern text recorded.
- Our published count they mirrored: `docs/about/competitive-matrix.md` and the `toke-tokenizer` README state "16K vocab, trained on 25,953 programs". Our 25,953 = `training-data-v03` (24,656 train + 1,297 eval, story 91.1.10).
- Our corpus is toke source; theirs is Python functions transpiled to Kern. No task ids or prompts can overlap; a content comparison is moot. `train.jsonl` (69,374 lines, `{text,type}`) carries no ids either.

**"Toke-16K" identified.** It is our own PyPI package `toke-tokenizer==0.1.0` (universal wheel sha256 `c33eee75…`, verified by download), whose `toke_tokenizer/data/tokenizer_v03.json` is byte-identical to `~/tk/toke-tokenizer/tokenizer_v03.json` (sha256 `42631f3a…`). Its vocab is **16,384 entries** — checked: `len(model.vocab) == 16384`. The epic's premise that "we never shipped a 16K" was wrong: we ship exactly one, on PyPI, with a README that says "16,384 tokens, trained on default-syntax toke source". Our own `tokenizer_v03.provenance.json` marks it `legacy: true`, "generator and inputs were not recorded; do not treat as reproducible" (131.24) — a gap on our side that a joint benchmark will expose.

**Licence / attribution.** `toke-eval`, `toke-model`, `toke-corpus`, `toke-tokenizer` are Apache-2.0 (NOTICE: "toke-model, Copyright 2026 M. Karwalski"). What KERN used from us: the 60 Python reference functions, the 1,000 generated `.toke` solutions and `data/gate1_token_counts.csv` from toke-eval at `851f6d8b`, and the tokenizer wheel. Apache-2.0 permits this use and any derivative benchmarking; it requires that redistributed copies carry the licence and NOTICE and mark modifications. KERN does not redistribute our files (it points at a pinned checkout and stores only hashes and counts), and it attributes by repository URL + commit in `README.md` and `benchmark_results/toke/README.md`. **Nothing in their use of our artefacts requires action.** Conversely, KERN's own lack of a licence means we cannot vendor it into toke-eval (§9).

## 7. Methodology audit against TEMSpec (task c)

TEMSpec (`toke-spec/docs/temspec.md`) separates §2.1 **same-tokenizer `token_reduction`** (toke vs baseline Python, same tokenizer — the gate metric), §2.3 **cross-language `density_ratio`** (informational, geometric mean of per-task ratios), and §6.2 **cross-language density with a purpose-built tokenizer** (informational "total stack" number). §6.3 requires every published number to state metric type, tokenizer(s), baseline and N.

| KERN claim | Classification | Comparable to toke's numbers? |
|---|---|---|
| Kern vs Python, cl100k/o200k (C1, C2) | Same-tokenizer reduction of a Python *re-encoding* vs Python. Formally the §2.1 shape (baseline = Python, same tokenizer). | Yes in form — but Kern's baseline is its own input. toke's §2.1 number compares two independently written programs; Kern's compares a deterministic transformation of one program. Kern's 28% and toke's 12.5% (Gate 1, 8K BPE) or the −80% (cl100k, complete programs) are honest on their own terms but answer different questions. |
| Kern vs toke, cl100k (C7) | §2.3 density ratio between two non-Python languages on the same tasks. Informational. | Yes, and it reproduces. The caveat is representativeness, not arithmetic: 60 five-to-twelve-line JSON-CLI functions generated by a 7B model in April, where the fixed harness (`m=…;i=j:std.json;i=s:std.str;f=main():i64{…j.print(x)}`) is a large share of every program. |
| Kern-16K vs Toke-16K (C12) | §6.2-type "each language with its own tokenizer". TEMSpec would never gate on it. | Only if both tokenizers see the syntax they were trained on and both hold the test set out. Neither holds here (§6.2). |
| Kern-16K vs Python + cl100k (C13) | §6.2 total-stack density. | Same kind of number as our "2.5–4×"/"52%" claims; comparable in spirit, on different tasks. |
| 541/542 "Pass@1" (C3) | Transpiler fidelity: Python → Kern → Python executed against EvalPlus tests. Deterministic; no model. | **Not a Pass@1 in toke's sense.** toke's Gate-1 58.8% (588/1,000; published as 63.7% = 588/923 until 2026-09-19, story 128.19) / Gate-2 100%-compile figures measure an LLM generating toke from a task prompt, scored on hidden tests. KERN has no equivalent published yet (their "current phase" is fine-tuning). |
| toke 29/60 (C7) | Compiler-compatibility of stale generated code + one smoke input per task. | Not a functional pass rate for toke in any published sense; KERN's own README says so. The number is real and is our artefact to fix. |
| "Reversible / round-trip" | Property of a transpiler. | toke has no Python fallback: `tkc` compiles to a native binary, and correctness is the binary's behaviour. A "transpile-to-Python then execute" criterion cannot be applied to toke, and "compile natively then execute" cannot be applied to Kern. The only shared criterion is *the same test inputs produce the same outputs*, which is what a joint benchmark should use. |

What is **fairly comparable** today: same-tokenizer cl100k and o200k counts on identical tasks with equalised harness overhead (both as JSON-CLI programs), reported as a density ratio with CIs; and output equality on shared tests. What is **not**: "Pass@1" across the two projects, the native-tokenizer lane as currently constructed, and any inference from the 60-pair subset to full programs.

## 8. Recommendation (task f)

**Respond — constructively — and fix our side. Do not ignore, and do not frame this as an error on their part.** Their arithmetic is right, their pins are exact, and their caveats are more careful than most. What needs saying is narrow and evidence-backed:

1. The 60 toke programs are April-2026 model output in a syntax three revisions old; the 29/60 measures our unrefreshed public artefact, not toke 2.8.0 or a toke model. We should publish 60/60-compiling v0.4 solutions for the same task ids (the 130.2 migration at HEAD is still 31/60) and offer them to the author for a rerun.
2. "Toke-16K" is `tokenizer_v03.json` and was scored on pre-v0.3 text; on migrated text the equal-vocab lane is 2,788 vs 2,872 (CI includes parity). Offer `kern-2026-08.repro.py` so they can reproduce that themselves.
3. Note that both native-tokenizer lanes need a held-out protocol on both sides before either project quotes one.

The owner decides whether and how to contact the author (no contact was made in this story; nothing here is confidential — every input is public).

**Bugs found on our side (to be filed by the owner — never fixed silently):**

- `tkc --migrate` leaves legacy `=`-equality in conditions (E2002 after migration; 20/60 here, 554/1,000 across the public set per KERN's audit).
- `tkc --migrate` leaves `as [T]` casts and `+[x]` literals (E1003 after migration; 20/60).
- toke-eval `benchmark/solutions/` at HEAD: 29/60 still fail `--check` after 130.2; `task-a-0042`/`0043` compile but produce wrong output (bubble sort with `arr.set(j; …)`) — needs a look at whether it is the program or the compiler.
- `tokenizer_v03.provenance.json` is `legacy: true`; the shipped PyPI wheel has no reproducible training record (131.24 already tracks this; it becomes externally visible now).
- `docs/about/competitive-matrix.md` and the tokenizer README state "52% average token reduction vs cl100k" without the §6.3 qualifiers (metric type = Toke-16K on toke text vs cl100k on toke text; N = 42). KERN read it correctly, but it invites the misreading "52% vs Python".

**A fair joint benchmark (feeds 133.2 / 133.3):**

- **Tasks:** one shared set with a Python reference *and* tests per task — the v0.4 held-out set from 128.1 (not the Gate-1 60), plus HumanEval+/MBPP+ where toke reference solutions exist (scope stated). Same JSON-CLI harness on both sides, or function-only on both sides; never mixed.
- **Sources:** both sides must compile/parse 100% before counting; failing tasks stay in the denominator and are reported. toke via `tkc --check` + `--min`; Kern via `transpile(compact=True)` + `compile_kern` parse.
- **Token lanes (TEMSpec §6.3 fields on every row):** cl100k and o200k same-tokenizer density ratios, geometric mean and sum-ratio with bootstrap CIs; python-minifier 3.2.0 as the shared minifier baseline; then, for 133.3, an equal-vocab lane where each side's BPE is trained on a disjoint corpus of the *same syntax era* and the task set is held out on both sides (Toke-16K must be re-trained on the v0.4 corpus under 116.9 first).
- **Correctness:** the same test inputs run against the toke native binary and against the Kern-compiled Python; report pass rates side by side; label them "reference-solution execution", not Pass@1. Model-generation Pass@1 is a separate lane, only once both projects have a fine-tuned model and a shared prompt format.
- **Runtime:** wall time and RSS of the toke binary vs the transpiled Python (KERN has no runtime of its own) — informational.
- **Publication:** methodology + per-task CSV + pinned commits and wheel SHAs, exactly as KERN did; offer the harness to the author before publishing.
