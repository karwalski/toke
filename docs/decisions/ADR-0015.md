**Date:** 2026-09-22
**Status:** **ACCEPTED** — ratified by the owner 2026-09-22. The toke toolchain is
C99 only. **pdfium, podofo and Tesseract are disqualified as vendored dependencies.**
Two escape hatches are open and are named below: a **C shim** around a C++ library,
and a **separate optional component** outside the default build.
**Deciders:** Matt Watt (ratified 2026-09-22)
**Story:** 135.0 (Epic 135) — gates 135.3 (`std.pdf`), 135.6 (platform OCR binding),
135.7 (Tesseract rejection record) and 135.8 (standalone `toke-ocr`)

## Context

Three separate requests in Epic 135 turn on one unwritten property of the build, so
the property is being written down as a decision rather than left to be rediscovered
(and re-argued) once per request:

- **135.3** — `std.pdf` text extraction, for which pdfium and podofo are the obvious
  candidate libraries. Both are C++.
- **135.6 / 135.7 / 135.8** — OCR, for which Tesseract is the obvious candidate. It
  is C++, and it additionally requires Leptonica.

The property itself:

- **The compile line is `-std=c99`.** `CFLAGS` in the `Makefile` begins
  `-std=c99 -D_GNU_SOURCE -Wall -Wextra -Wpedantic -Werror`. The compiler is driven
  through `CC = cc` and links with `LDLIBS = -lm -lz -lpthread`. There is no `CXX`,
  no `CXXFLAGS`, and no C++ link step anywhere in the build.
- **The build contains zero C++ translation units.** Every source in `SRCS`,
  `STDLIB_SRCS` and the vendored sets is `.c`. The vendored libraries chosen so far
  are all C: cmark (`stdlib/vendor/cmark/src/*.c`), tomlc99, miniz.
- **The tracked repository contains zero C++ files.** Verified against the index,
  not the working copy: `git ls-files` returns no `.cpp`/`.cc`/`.cxx`/`.hpp` at all.
  The vendored cmark drop is whitelisted in `.gitignore` down to
  `cmark/COPYING` and `cmark/src/*.{c,h,inc}`, so cmark's upstream `api_test/`
  directory — which contains a `cplusplus.cpp` — is never committed and is absent
  from a fresh clone. A stale `api_test/cplusplus.cpp` can survive in a *working
  copy* that once held a full upstream checkout; it is untracked, never compiled
  (the Makefile takes cmark only from `$(wildcard stdlib/vendor/cmark/src/*.c)`),
  and is not a counterexample.

**Why this is an architectural decision and not a Makefile detail.** Vendoring a C++
library does not add a dependency to one module; it adds **a C++ toolchain
requirement to every build of toke on every platform, permanently**. It changes the
link driver, the standard-library runtime the binary depends on (`libstdc++` /
`libc++`), the set of machines that can bootstrap the compiler, and the cross-compile
and static-link stories — for every user, forever, including those who never touch
PDFs or OCR. That is a decision about what toke *is*, and it should not be made in
order to read a bank statement.

## Decision

**The toke toolchain is C99 only.** The default build compiles C99 with `cc` and
links with a C link line. No C++ translation unit may enter the default build, and
**no C++ library may be vendored into it**.

Consequently, **pdfium, podofo and Tesseract are disqualified as vendored
dependencies.** This is a decision about *vendoring into the default build*, not a
judgement about the libraries' quality, and not a refusal of the capabilities they
would provide.

## Escape hatches — what *would* be considered

This constraint has known routes through it. A future request for a C++-backed
capability should be evaluated against these two, not refused outright:

**1. A C shim around a C++ library (out-of-tree, dynamically linked).**
The C++ library is *not* vendored. It is built separately and exposes a narrow
`extern "C"` surface; toke binds to that surface through `dlopen`/`dlsym` or a link
against a system-installed shared library, with the capability compiled out — or
degrading to a clear runtime error — when the library is absent. The toke build stays
C99 and keeps working on a machine with no C++ toolchain; only users who want the
capability need the library. **This is the route to prefer** when a C++ library is
genuinely the best implementation of a capability that belongs in the stdlib.
The shim must be thin enough that it carries no policy: marshalling and lifetime
only, so the C++ surface cannot leak into toke's semantics.

**2. A separate optional component outside the default build.**
The capability ships as its own repository and its own binary, which toke invokes as
a subprocess (argv-only, per ADR-0011) or talks to over a defined protocol. The
component may be written in whatever language suits it. Nothing about it touches the
toke build, and a user who does not install it loses only that capability.
This is the route already chosen for OCR: **135.8, the standalone `toke-ocr`
repository.**

A third route, always available and always preferred where it exists, is a **platform
binding**: use the capability the operating system already provides through its C
interface — which is what **135.6** does for OCR (Vision on macOS, and the
equivalent per-platform API elsewhere). It adds no dependency at all.

## Consequences

- `std.pdf` (135.3) must be implemented either in C, or via hatch 1 or 2 — not by
  vendoring pdfium or podofo. The implementation route is now decided in the sense
  that the disqualified options are off the table; the choice among the remaining
  ones belongs to 135.3.
- Tesseract's rejection as a vendored dependency is settled; **135.7** records it
  with this ADR as the decisive reason, and routes the requirement to 135.6 and
  135.8.
- **135.9's reply must name this decision explicitly**, since it is the reason the
  OCR answer is a platform binding plus a separate repository rather than the obvious
  "vendor Tesseract".
- Any future proposal to vendor a C++ library must first propose *amending this ADR*,
  and must account for the cost it imposes on every platform's build — not only on
  the platform where the proposer happens to be working.
- The C99 constraint is not costless and is not pretended to be: it excludes some
  mature, well-tested libraries, and the alternative implementations may be more work
  or lower fidelity. That cost is accepted in exchange for a build that needs only a
  C compiler.

## Alternatives considered

- **Vendor the C++ library and add a C++ toolchain requirement.** Rejected. It is
  the largest possible blast radius for the smallest possible constituency: every
  build on every platform pays, so that some users can read PDFs. It also compounds —
  the first C++ dependency is the expensive one, and once paid, every subsequent
  "it's already C++ in here" argument gets easier.
- **Vendor it behind an optional `make` flag, still in-tree.** Rejected as the
  default answer. It keeps the C++ source in the repository and in the maintenance
  surface, and an optional path that is rarely built is an optional path that is
  rarely *working*. Hatch 1 achieves the same user-visible result without the source
  in-tree. (Hatch 2 is this idea taken to its honest conclusion: a separate component
  with its own repository, build and tests.)
- **Find or write a C equivalent.** Always preferred where one exists and is
  adequate — this is how cmark, tomlc99 and miniz were chosen. It is not always
  available at acceptable quality, which is why the two hatches exist.
- **Relax to C11 or later.** Out of scope here: this ADR is about the C/C++
  boundary, not about which C standard. Moving to a later C standard is a separate,
  much cheaper decision and is not foreclosed by this one.
