**Date:** 2026-05-30
**Status:** accepted
**Deciders:** Matt Watt

## Context

Pre-v0.3.x toke supported two ways to build strings:

1. `+` operator overloaded for `$str + $str` — implemented in codegen via
   `tk_str_concat` dispatch (`llvm.c`), listed as an operator overload in the
   spec Appendix D operator table.
2. `s.concat(a; b)` — a stdlib function call.

The type checker (`types.c`) rejected `+` on strings per `semantics.md §2.4`
("Arithmetic operators: both operands must be numeric"). Codegen accepted it.
Type-checker rejection only fired in some contexts (return, assign) and not
others (let-binding init, because `NODE_BIND_STMT` does not re-infer the init
expression). This inconsistency produced misleading diagnostics like
`"type mismatch: expected 'str', got 'str'"` and silently corrupted the
generate-compile-repair loop: models that wrote `r = r + part + sep` in a loop
saw a useless error in some sites and clean compilation in others, then trained
to believe both forms were valid.

Audit of the 2,065-program corpus surfaced this as the root cause of at least
10 `E4031` "expected str got str" failures and an undetermined fraction of the
670 `E2002` failures where the model could not parse its own diagnostic and
went off the rails for the remainder of its repair budget.

In parallel, downstream projects building on toke (loke in particular) reported
that the natural way to build a string in a loop —
`r = mut.""; lp(let i=0;i<n;i=i+1) { r = r + parts.get(i) + sep }` —
allocates a fresh string per iteration. For N parts this is O(N²) bytes copied:
the same trap Java, JavaScript and Python developers learned to avoid by using
`StringBuilder` / `join` / `"".join()`. Toke had no equivalent first-class
construct.

## Decision

1. **`+` is strictly numeric.** `types.c` enforces the `semantics.md §2.4`
   rule with no exceptions. `llvm.c` removes the `tk_str_concat` dispatch from
   the `+` codegen path. Any program that uses `+` on string operands is
   rejected at type-check with a new `E4031` message that points to the three
   canonical alternatives.

2. **Three canonical patterns for string building**, each covering a distinct
   shape with no overlap:

   - **Interpolation** for templates with mixed literals and expressions:
     `"hello \(name): \(count)"`. The interpolation form is the primary
     pattern in v0.3.x onward. The toke BPE tokeniser compresses `\(` as a
     single dense token. Lowered at codegen time (story 111.5a) by
     synthetic-parsing each `\(expr)` and emitting a chain of
     `tk_str_concat` calls — one per segment. Interpolated expressions
     must evaluate to `$str` (use `s.fromint(n)` / `s.format(f;"%.4f")` /
     `n as $str` for non-string values).

   - **`s.join(arr: @$str; sep: $str): $str`** for delimiter-joined
     collections. Single allocation. Replaces the loop-accumulator pattern
     that previously triggered the O(N²) issue.

   - **`s.builder(): $strbuilder`** with `b.add(s)` / `b.build()` for true
     dynamic accumulation patterns (logs, code generation, large blobs).
     Single backing buffer that grows; build() finalises. O(N) total.

3. **`s.concat`** stays in the stdlib as a variadic helper
   (`s.concat(parts: @$str): $str`) but is **secondary** to interpolation. It
   is the right answer when the list of parts is already an array, e.g. when
   building from a function argument.

4. **No new operators.** A dedicated `++` for string concat was considered and
   rejected — it adds a lexer token, mildly violates the 55-char ergonomic
   target, and is strictly worse than interpolation for the dominant
   template-with-variables shape.

## Rationale

This decision is evaluated against the four core toke objectives:

- **Token efficiency.** Interpolation is the most compressible form for the
  toke BPE: `\(` is a near-unique bigram with no presence in non-toke corpora,
  so the tokeniser merges it to a single token. `+`-overloaded concat splits
  its information content across numeric and string contexts, halving the
  per-merge density. For a typical template, interpolation is ~50% denser than
  the equivalent `+` chain.

- **Single canonical form.** Each use shape has exactly one correct answer:
  templates → interpolation; collections → join; dynamic accumulation →
  builder. Models converge faster on canonical patterns than on
  "could-be-anything" operator overloads.

- **Type-system orthogonality.** `+` stays as a single, predictable arithmetic
  operator. `semantics.md §2.4` no longer contradicts the operator table and
  the codegen. Diagnostics gain clarity: a mismatched `+` site now produces
  exactly the same `E4031` regardless of context.

- **LL(1) preservation.** The decision is purely a semantic/type-system
  change. The parser sees `Expr "+" Expr` regardless of operand types, so
  ADR-0001's LL(1) guarantee is unaffected. The interpolation form was
  already in the language (lexer test L009) so no new productions are added.

## Consequences

**Positive:**

- The misleading "expected 'str', got 'str'" diagnostic disappears.
- The O(N²) string-loop trap is no longer reachable via `+`; the canonical
  alternative (`s.join` or `s.builder`) is O(N).
- LLM models trained on the new prompt converge on one canonical form per
  use case instead of branching across `+`, `s.concat`, and interpolation.
- Future tokeniser retrains compress the dominant template pattern to near-
  optimum.
- Codegen path for `+` is simpler (no type-dispatch at use site).

**Negative:**

- Breaking change for any current toke program that uses `+` on strings. We
  estimate this affects a substantial fraction of the 2k-program corpus and
  some downstream projects (loke, ooke, moke, toke-website).
- Existing LLM models (Claude, GPT, etc., trained on Python/JS/Java) emit
  `+` on strings reflexively; we accept the prompt-engineering cost.
- Migration tool (`tkc --migrate-strconcat`) is required to update existing
  source automatically. Ambiguous cases need manual review.

## Migration

A new compiler flag `tkc --migrate-strconcat <file>` rewrites every
`NODE_BINARY_EXPR{TK_PLUS}` whose both operands are `TY_STR` into the most
appropriate canonical form, by shape:

| Source shape | Rewrite |
|---|---|
| All-literal: `"a"+"b"+"c"` | Single literal `"abc"` |
| Literals + identifiers, ≤4 parts: `"k="+v` | Interpolation `"k=\(v)"` |
| 5+ parts with mixed shapes | `s.concat(@(part1;part2;…))` |
| In-loop accumulator `r=r+x+sep` | `s.builder()` + a manual hint flag |
| Unambiguous `arr.join(sep)` equivalent | `s.join(arr;sep)` |

The migration tool runs in-place with a `--check` mode that lists rewrites
without applying them. Ambiguous cases are flagged and require manual review.

## Alternatives considered

1. **Keep `+` as operator overload, fix only the type-checker** (option A in
   the design review).
   Easiest path; matches current model behaviour. Rejected because it
   permanently couples `+` to two unrelated operations, splits BPE merge
   information, and silently locks in the O(N²) loop trap.

2. **Disable `+` codegen for strings AND require `s.concat` only**
   (option B in the design review). Strictly enforces `semantics.md §2.4` but
   produces verbose deeply-nested calls
   (`s.concat(s.concat(a; b); c)`) for the dominant template shape — about
   2.5× the token count of interpolation. Rejected as worse for token
   efficiency without compensating clarity.

3. **Add a dedicated `++` operator for string concat** (option D). Token-
   efficient and type-clean, but adds a lexer token and is strictly inferior
   to interpolation for templates. Operator-overload psychology persists.
   Rejected.

4. **Hold and decide later.** Rejected because the inconsistency was
   actively producing misleading diagnostics in the audit and the canonical
   pattern (interpolation) was already in the language but underused.
