## Context

The extended investigation found that toke has **zero post-quantum or hybrid support,
no crypto-agility layer, and no doc/log warning about quantum risk** — and, more
fundamentally, that its cryptographic *formats are not self-describing*, so a future
migration to any new algorithm has no in-band way to happen non-breakingly. This ADR is
the **prerequisite** for the PQC roadmap (122.5), the quantum-safe docs/warnings (122.6),
and the crypto point-fixes (121.20): agility must be designed before algorithms are
changed. The concrete state:

- **Ciphertext is bare and unversioned.** AES-256-GCM output is `ct\|\|tag` with no
  version byte, no algorithm tag, no envelope header (`encrypt.h:37`); ChaCha20-Poly1305
  likewise (`encrypt.h:123`). A stored ciphertext is **not self-describing** — you cannot
  tell at decrypt time which algorithm produced it, so you cannot introduce a second one
  without an out-of-band scheme or a breaking change.
- **JWT `alg` is a hardcoded string literal** (`"...HS256..."`, `auth.c:75`); verify
  always recomputes HMAC-SHA-256. There is no algorithm registry and no negotiation —
  swapping to any other signature is a new code path, not a config change. (The upside:
  this is *why* there is no alg-confusion bug today.)
- **Each primitive is a fixed-name function** (`encrypt.aes256gcm_encrypt`,
  `encrypt.rsa_sign`, …); callers bind to a concrete algorithm at the API surface. There
  is no `Cipher`/`Signer` abstraction, no suite negotiation, no format versioning. RSA
  uses a **bespoke non-DER binary key format** (`encrypt.h:154-166`).
- **Harvest-Now-Decrypt-Later exposure is real.** Quantum-vulnerable asymmetric crypto
  protects long-lived material: RSA-OAEP at-rest encryption (`encrypt.h:179`),
  X25519-DH-derived session/shared secrets (`encrypt.h:65`), classical TLS 1.3 ECDH
  (`tls.c` sets **no** KEX group, `tls.c:189-258`), and Ed25519/ECDSA-P-256 signatures on
  long-validity artifacts — ACME-issued certs (`acme.c:74`) and release binaries (cosign
  ECDSA). Recorded traffic / stored ciphertext is decryptable once a CRQC exists; signed
  artifacts become forgeable. (JWTs are HS256/symmetric — the one bright spot.)
- **The crypto lives in two domains.** A bundled, **libc-only** hand-rolled C core
  (`crypto.c`/`encrypt.c`, "no dependencies beyond libc", `crypto.h:11`) and an
  **OpenSSL 3.6.1** TLS/ACME layer (`Makefile:204-207`). OpenSSL 3.6.1 *can* do
  `X25519MLKEM768` hybrid KEX via a provider, but `build_ssl_ctx` sets no group, so the
  negotiated exchange stays classical. The libc-only core means PQC cannot be gained "for
  free" by upgrading a library.
- **No doc, log, or warning anywhere** mentions PQC, quantum, crypto-agility, or
  asymmetric-algorithm deprecation.

The common thread: **the formats carry no algorithm identity, so nothing can evolve.**
The fix is an agility layer first; specific algorithm swaps (including PQC) ride on it.

## Decision

Adopt **crypto-agility-by-construction**. Sub-decisions are independent and can be
ratified separately; (a)–(c) are the foundation and are recommended now, (d)–(e) are the
roadmap, (f) is documentation.

### (a) Versioned, algorithm-tagged envelope for at-rest crypto — **Recommend: adopt now**

Wrap every `encrypt.*` symmetric/asymmetric output in a self-describing envelope:

```
magic(2) | version(1) | alg_id(1) | nonce_len(1) | nonce(n) | ciphertext | tag(16)
```

- Decrypt dispatches on `alg_id`; new algorithms are additive (`alg_id` values), never a
  breaking reinterpretation of old bytes.
- **Backward compatibility:** reserve `version = 0` / a distinct magic for "legacy bare
  `ct\|\|tag`, implicitly AES-256-GCM," so existing stored ciphertext still decrypts; new
  writes emit `version = 1` tagged envelopes. Audit every caller of `aes256gcm_*` /
  `chacha*` / `rsa_*` for hard-coded format assumptions (`encrypt.c`).
- This is the single highest-leverage change: without it, *no* future migration (PQC or
  otherwise) is non-breaking.

### (b) JWT / token algorithm dispatch with a verifier allowlist — **Recommend: adopt now**

- Replace the hardcoded header (`auth.c:75`) with an `alg` registry; sign takes an
  explicit algorithm; verify dispatches on the token's `alg` **only after checking it
  against a caller-supplied allowlist**. Never trust the token's `alg` blindly, and
  **reject `alg: none`** — this preserves today's accidental safety while enabling
  RS256/ES256/EdDSA and, later, ML-DSA.
- Default stays HS256 (compatible); the allowlist is per-verifier and explicit.

### (c) Enable hybrid post-quantum TLS KEX — **Recommend: adopt now**

Set `X25519MLKEM768` (with classical fallback) as a preferred group in `build_ssl_ctx`
(`tls.c:189-258`) via the already-linked OpenSSL 3.6.1 provider. This is transparent to
callers (negotiated), low-risk, and directly blunts HNDL on recorded TLS traffic — the
biggest passive-capture exposure. Gate behind the `TK_OPENSSL` build (the default stub
build has no TLS anyway).

### (d) Signature-scheme agility + PQC roadmap — **Recommend: plan, phased**

Extend the envelope/registry approach to signatures and plan migration of
Ed25519/ECDSA-P-256 → ML-DSA (FIPS 204) or SLH-DSA (FIPS 205) for: ACME account/cert keys
(`acme.c:74`), release signing (cosign/Fulcio), and app-level signatures. Assess
cert-chain and interop impact; this is a roadmap item (122.5), not an immediate flip.

### (e) Underlying-library strategy for PQC primitives — **Recommend: vetted library, never hand-rolled**

The libc-only core (`crypto.h:11`) must **not** grow a hand-rolled ML-KEM/ML-DSA — PQC
primitives are exactly the kind of code that must come from a vetted implementation.
Decision: PQC primitives are provided via **OpenSSL 3.5+ providers / liboqs**, gated
behind the `TK_OPENSSL` build; the bundled libc-only core remains **classical-symmetric
only** (AES-256-GCM, ChaCha20-Poly1305, SHA-2, HMAC, HKDF/PBKDF2/bcrypt — all already
quantum-adequate at 256-bit). This keeps the zero-dependency default build classically
secure while making PQC an opt-in, library-backed capability.

### (f) Docs, runtime warnings, deprecation track — **Recommend: adopt (story 122.6)**

- Add a PQC / crypto-agility posture section to `docs/security/threat-model.md` and
  `stdlib/encrypt.md`: classical asymmetric (RSA/X25519/ECDSA/Ed25519) is
  quantum-vulnerable; symmetric/hash primitives at these sizes are adequate; guidance on
  HNDL for long-lived data.
- Open a deprecation track for classical-asymmetric-only protection of long-lived data
  per `docs/governance.md:79`.
- Consider a build-time or runtime **advisory** when a quantum-vulnerable primitive is
  used to protect long-lived/at-rest data (the "warning in docs/logs" the owner asked
  for) — e.g. a one-line note from `rsa_encrypt` usage in the security posture and,
  optionally, a debug-level log line.

## Quantum-readiness summary

| Primitive | Use | Quantum status | Action |
|---|---|---|---|
| AES-256-GCM, ChaCha20-Poly1305 | at-rest / AEAD | adequate (256-bit) | envelope-tag (a) |
| SHA-256/512, HMAC, HKDF/PBKDF2/bcrypt | hash/MAC/KDF | adequate | none |
| RSA-2048/4096 (OAEP/PSS) | encrypt/sign | **vulnerable** | HNDL triage (d), envelope (a) |
| X25519 ECDH | key exchange | **vulnerable** | hybrid KEX (c/d) |
| Ed25519 / ECDSA-P-256/384 | signatures | **vulnerable** | migrate ML-DSA/SLH-DSA (d) |
| TLS 1.3 KEX | transport | **classical only** (no group set) | enable hybrid (c) |
| JWT HS256 | tokens | symmetric — OK | alg-dispatch/allowlist (b) |

## Migration & compatibility impact

- **(a) envelope — mostly compatible via the version-0 legacy path;** the only cost is a
  small header per ciphertext and a caller audit for format assumptions. New format is
  the write default; old ciphertext still reads.
- **(b) JWT — compatible;** HS256 remains the default, the allowlist is additive, and
  `alg: none` rejection only closes an attack.
- **(c) TLS hybrid — transparent;** negotiated, classical fallback preserved. Requires the
  `TK_OPENSSL` build.
- **(d/e) — roadmap, no immediate breakage;** the library-gating means the default
  libc-only build is unaffected until a PQC path is opted into.
- Ties the crypto point-fixes: the RNG fail-open (CRY-01), RSA-OAEP Manger oracle
  (ENC-02), and missing zeroization (HYG-01) fixes in 121.20 touch the same code and
  should land on top of the envelope work, not before it.

## Consequences

- toke gains a migration path for *every* cryptographic format — the precondition for PQC
  and for any future algorithm change — instead of formats frozen by their lack of a
  version field.
- HNDL exposure on TLS traffic is addressed immediately (c); at-rest and signature
  exposure get a staged plan (d).
- The zero-dependency default build stays classically secure; PQC is a vetted,
  library-backed, opt-in capability — no hand-rolled post-quantum crypto.
- Unblocks the quantum-safe warnings (122.6) the owner requested and gates the 121.20
  crypto fixes.

## Decision needed

Ratify the foundation now — **(a)** versioned algorithm-tagged envelope, **(b)** JWT
alg-dispatch + allowlist (+ reject `none`), **(c)** enable hybrid `X25519MLKEM768` TLS KEX
— and approve the direction for **(d)** signature/PQC roadmap, **(e)** library-backed
(never hand-rolled) PQC primitives, and **(f)** the docs/warnings/deprecation track.
**Awaiting owner decision before any code is written.**
