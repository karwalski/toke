**Date:** 2026-11-10
**Status:** decided and implemented — **display only**; one owner option recorded below (an executable variant), which does not block the flag
**Story:** 96.7 (v0.4 deliverable; "Python decompiler view", an enterprise-procurement requirement from the 2026-05 research review, `docs/spec/training-next-phase.md` and Gate 3 criterion in `docs/spec/gate3-criteria.md`)
**Written before the implementation.** The rendering rules below are what the printer implements; the golden files in conformance case C1210 hold it to them.

## The requirement, and what it does not say

The research review's finding was that a reviewer who does not read toke cannot sign off on toke code, so toke needs a "human-readable translation" into a language that reviewers already read. Python is that language. The requirement is for a **view**: something a security reviewer, auditor or procurement checklist can read line by line next to the toke source.

It does not ask for a transpiler, and the note does not build one. Three properties of toke make executable Python a different and much larger product. They are listed under [owner option](#owner-option) below.

## What it is

`tkc --python-view FILE...` parses each file and prints a Python-like rendering of it to stdout, then exits. Like `--fmt`, `--dump-ast` and `--min`, it is a **fast-path mode**: no name resolution, no type check, no code generation, no stdlib lookup. It runs on any file that parses.

| Property | Guarantee |
|---|---|
| Display only | The output is **not executable** and **not round-trippable**. It opens with a five-line header that says so, and that toke semantics apply to everything shown. |
| Deterministic | The output is a pure function of the source bytes and the file's basename. Two runs are byte-identical, and the path used to name the file on the command line does not matter (C1211). |
| Faithful structure | Every function, statement and expression in the AST appears, in source order, with the same nesting. Nothing is summarised or elided. Loops keep their exact evaluation order (see `lp` below). |
| No partial output | A file that does not parse prints nothing on stdout, exits 1, and emits the parser's structured diagnostics, exactly as `--check` does. |
| Python syntax | Not promised. Measured on 2026-11-10, every one of the 580 `.tk` files in this tree that parse renders to text that `ast.parse` accepts, and C1211 checks this for `examples/` and the fixtures. It is a property of the printer and makes the output easy to highlight and diff. It is not a promise that the text runs. |

It is **not** a type-annotated view. Types appear where the source wrote them (parameters, returns, typed `let`, constants, type declarations). Inferred types are not shown, because showing them would make the view depend on the type checker. The view would then fail on any file with a type error, which is when a reviewer most needs to read it.

## Where it sits

The flag is a printer over the parser's AST, next to the two existing AST printers:

- `src/ast_json.c` — `--dump-ast`, JSON for tools
- `src/fmt.c` — `--fmt` / `--pretty`, canonical toke
- **`src/pyview.c`** — `--python-view`, Python for people

`src/main.c` dispatches the flag in `process_file()` straight after the parse, before `--lint`. The companion file (`--companion`, `src/companion.c`) was considered as a home and rejected. A companion is a Markdown skeleton with a source hash, meant to be checked in and edited by hand. The view is throwaway output, so it does not belong in a file that `--verify-companion` checks.

## Rendering rules

| toke | Python view |
|---|---|
| `m=a.b;` | `# module a.b` |
| `i=x:std.io;` | `import std.io as x` |
| `t=$p{x:i64;y:$str};` | `@dataclass` / `class p:` with `x: int`, `y: str` |
| `t=$e{$a:i64;$b:$str};` (sum type) | `class e(SumType):  # holds exactly one of the variants below` with `a: int`, `b: str` |
| `lim=5:i64;` | `lim: int = 5` |
| module-level `let s=mut.$p{..}` | `s = p(..)  # mut` |
| `f=g(a:i64):i64!$e{..}` | `def g(a: int) -> Result[int, e]:` |
| extern `f=g(a:i64):i64;` | `def g(a: int) -> int: ...` |
| `i64`, `f64`, `void` | `int`, `float`, `None` |
| `$str`, `bool`, user `$t`, `alias.$t` | `str`, `bool`, `t`, `alias.t` |
| `i32`, `u8`, `u64`, `f32`, ... | kept as written (fixed width is meaning a reviewer needs) |
| `@T`, `@(K:V)`, `*T`, `(A;B):R` | `list[T]`, `dict[K, V]`, `Ptr[T]`, `Callable[[A, B], R]` |
| `let x=e` / `let x:T=e` / `let x=mut.e` | `x = e` / `x: T = e` / `x = e  # mut` |
| `x=e` | `x = e` |
| `<e`, `rt e` | `return e` |
| `br` | `break` |
| `if(c){..}el if(d){..}el{..}` | `if c:` / `elif d:` / `else:` |
| `lp(c){..}` | `while c:` |
| `lp(let i=0;i<n;i=i+1){..}` | `i = 0` / `while i < n:` / body / `i = i + 1` |
| `mt v {$ok:x ..; $err:e ..}` | `match v:` / `case ok(x):` / `case err(e):` |
| `{arena ..}`, `sc{..}`, `spawn e` | `with arena():`, `with scope():`, `spawn(e)` |
| `a.get(i)` | `a[i]` |
| `x as f64` | `float(x)` |
| `x!$e` | `propagate(x, e)` |
| `$p{x:1}` / `$e{$a:1}` | `p(x=1)` / `e.a(1)` |
| `@(1;2)` / `@(k:v)` / `@()` | `[1, 2]` / `{k: v}` / `[]` |
| `"v=\(x)"`, a string over several lines | `f"v={x}"`, `"""..."""` |
| `&f`, `&m.f` | `f`, `m.f` |
| `&&`, `\|\|`, `!` | `and`, `or`, `not` |
| `true`, `false` | `True`, `False` |
| an identifier that is a Python keyword (`in`, `class`, `pass`) | gets a trailing underscore (`in_`, `class_`, `pass_`) |

**Precedence.** The parser keeps no parenthesis nodes. The printer brackets each operand by **Python's** precedence rules, applied to toke's tree. Where the two languages disagree, the tree wins. For example, toke binds `==` tighter than `&` and Python does not, so toke `a&b==c` prints as `a & (b == c)`. Comparisons never chain: toke `(a<b)==c` keeps its parentheses.

**`lp` with three clauses.** It prints as an init, a `while`, and the step as the last statement of the body. toke has no `continue`, so the step always runs last and `br` skips it in both languages. The rendering is therefore exact. A `for i in range(..)` rendering was rejected because `range` evaluates its bound once and toke evaluates the condition on every iteration.

**`if` and `mt` as values.** toke's `if` and `mt` are expressions. Python's `match` is not, and Python's conditional expression holds single expressions only. The printer applies three rules in order:

1. An `if` whose every branch is a single expression prints as a conditional expression: `k = a if a > 1 else 0`.
2. When the value goes straight into a `let`, an assignment, a `return` or an expression statement, the statement form is printed with the value **routed** into each branch: `x = ...` or `return ...` as the last line of every branch. This is how `let r=mt f(a) {..}` reads.
3. Anywhere else, for example as a call argument, the `if` or `mt` is **lifted** into a local `def _ifN():` / `def _mtN():`. The helper is printed just before the statement and called in place. Lifting changes nothing about evaluation order, because a `def` evaluates nothing. When a lifted body contains a toke `<`, a comment line in the helper says that it returns from the enclosing function, not from the helper.

**Closures.** `let f=fn(..){..}` prints as a nested `def f(..)`. A closure whose body is one expression prints as `lambda`. Any other closure inside an expression is lifted to `def _fnN(..)`, using rule 3. Helper numbers count up from 1 in source order within each file, which keeps the output deterministic.

## What it does not render

- **Comments.** The AST does not carry them. `--fmt` recovers them from a second scan of the source, and the view could do the same later. It is not a correctness issue, because the view never claims to show comments.
- **Inferred types** (see above).
- **Semantics Python would change.** Integer `/` truncates toward zero, and `%` takes the sign of the dividend. Fixed-width integers wrap or trap as toke defines. A lifted helper reads outer variables at call time and does not write them. The header says that toke semantics apply. These are the reasons the view cannot be executable without becoming a transpiler.

## Owner option

**Executable Python, or a Python stub that type-checks: not decided, not blocking.** A procurement checklist might one day mean "runs in Python" rather than "readable as Python". That would be a separate product with its own story, because it needs:

- a runtime shim for toke's integer widths, `/` and `%` semantics, arenas, `sc`/`spawn` and the `T!E` error union
- a Python binding for every stdlib module a program imports
- a decision on whether the shim or the compiled toke binary is the reference when they disagree

**Recommendation:** keep `--python-view` display only, which is what the requirement asks for. File an executable variant only when a named customer asks for it.
