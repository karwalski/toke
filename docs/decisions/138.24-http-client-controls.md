**Date:** 2026-11-15
**Status:** **accepted** — a spec amendment to [the normative stdlib signatures](/docs/spec/stdlib-signatures/) (`std.http`, and a new `std.net` entry). Decided by the owner on 2026-11-15, items 2.1, 2.2 and 2.3 of `docs/owner-decisions-2026-11-12.md` ("Answers recorded later on 2026-11-15"). Implemented with this record.
**Stories:** 138.24 (deadline and body cap), 138.25 (connect address and resolver), 138.27 (header-carrying GET), 138.34 (the `timeoutms` documentation). loke handoffs 2026-11-09 (T-63, T-58 addendum) and 2026-11-15.

## The problem

loke fetches URLs it does not control (moke's `/api/proxy`, its update checks). The `std.http` client could not do that safely, so loke shells out to `curl` with `--max-time`, `--max-filesize` and `--resolve`:

1. **No bound on a request as a whole.** The client's only clock is `timeoutms`, which is `SO_RCVTIMEO` on the socket. That timeout restarts on every byte, so a server that sends one byte inside each timeout holds the caller for as long as it likes. loke measured this on v3.2.0: a server sending one body byte every 5 s held `http.geturl` for 40,383 ms, and the call answered `$ok`.
2. **No bound on the body.** A response body was read whole into memory. A 64 MiB body answered `$ok`.
3. **No way to pin the address.** The client resolves the URL's host inside connect and takes the first address that answers. A caller that resolves a name, checks every address against its rules (private, loopback, link-local, cloud metadata) and then fetches the URL lets the name be resolved a second time, to whatever it answers then. This is DNS rebinding. std had no general resolver either: the only `resolve` was `mdns.resolve`.
4. **No GET that carries headers.** Only `http.geturl(url)` and `http.clientget(c;path)` existed. The GitHub API refuses a request without a `User-Agent`.

A fifth problem was in the documentation: `docs/stdlib/http.md` called `timeoutms` a "per-request timeout". It is a per-read timeout (138.34). A whole-request deadline and `timeoutms` must not be two names for one idea.

## The owner's answers (2026-11-15)

| Item | Answer |
|---|---|
| 2.1 (138.24, 138.34) | **(a) opt-in controls on the HTTP client, defaults off:** a whole-request deadline covering connect, TLS handshake, headers and body, and a body cap that stops the read and answers `$err` for an over-cap body. Defaults are revisited at the next major. One spec amendment with 2.2 and 2.3, which also corrects the per-read `timeoutms` documentation. |
| 2.2 (138.25) | **A client option `connectaddr`** (connect to a caller-checked address while SNI and certificate verification use the URL's host) **plus `net.resolve`** returning every address, gated by the `net` capability. |
| 2.3 (138.27) | **Accept as proposed:** `http.getheaders(url;headers)`, typed like `http.postheaders`, with 138.8's header rules (Host and Content-Length reserved, CR/LF refused). |

## The amendment

Signatures use the v0.4 notation of `docs/spec/stdlib-signatures.md`. Each one is declared in `stdlib/http.tki` or `stdlib/net.tki`.

### 1. Client options (138.24, 138.25)

```text
f=http.withdeadline(c:$httpclient;ms:u64):$httpclient
f=http.withmaxbody(c:$httpclient;bytes:u64):$httpclient
f=http.withconnectaddr(c:$httpclient;addr:$str):$httpclient
```

They follow `http.withproxy`, the one client option std already had. Each returns a **copy** of `c` with one setting changed, and `c` itself is unchanged. They compose: `http.withmaxbody(http.withdeadline(c;5000);1048576)`. A client from `http.client` has none of them, so every existing call behaves as before.

They apply to the client's request calls: `http.clientget`, `http.clientpost`, `http.clientput` and `http.clientdelete`. `http.stream` and `http.downloadfile` read on separate code paths that these controls do not reach, so they **refuse** a client that carries any of the three. `http.stream` answers `$err`, and `http.downloadfile` returns `-1`. Ignoring a security control without saying so would be worse than refusing it.

**`http.withdeadline(c;ms)`**: each request must finish within `ms` milliseconds of the call. The bound covers connecting (and the proxy `CONNECT`, when there is a proxy), the TLS handshake, sending the request, the response headers and the response body. A request that runs past it is `$err` with `code` 0, and its `msg` begins `request deadline exceeded (<ms> ms)` followed by the stage it reached:

- `during connect`
- `during the proxy CONNECT`
- `during the TLS handshake`
- `while sending the request`
- `before the header block ended (<n> bytes)`
- `after <n> of <m> body bytes (Content-Length)`
- `before the last chunk of a chunked body (<n> body bytes decoded)`
- `after <n> body bytes of a body with no Content-Length (...)`

A deadline of `0` has already passed, so every request fails at once. No value turns the deadline off: to drop it, use the client the deadline was added to.

`timeoutms` keeps its meaning: it is the time allowed for **each read**, and it restarts whenever data arrives (138.34). The deadline counts from the call and does not restart. A request with a deadline is still subject to `timeoutms` on each wait, and a wait that runs out its `timeoutms` reports `receive timed out` exactly as before.

The deadline does **not** interrupt a host-name lookup. `getaddrinfo` cannot be interrupted, so the deadline is checked before the lookup starts and again when it returns. With `http.withconnectaddr` no lookup happens at all.

**`http.withmaxbody(c;bytes)`**: a response whose body is longer than `bytes` is `$err` with `code` 0. Its `msg` begins `response body exceeds the cap (<bytes> bytes)`. The read stops at that point: the connection is closed with the rest unread, and no partial body is ever answered `$ok`. The check depends on how the body is framed:

- **`Content-Length`:** a length over the cap is refused before any of the body is read.
- **Chunked:** the body is refused on the chunk-size line that would take it past the cap, before that chunk's data is read. Bytes already decoded are dropped from the read buffer. The bytes held for one unfinished chunk, size line or trailer line may not pass the room the cap has left plus 8 KiB, so a size line, extension or trailer line longer than that is refused too.
- **Neither header (the body ends when the connection closes):** the body is refused as soon as it passes the cap.

A body exactly `bytes` long is `$ok`. The cap is on the body as the response delivers it (`r.body`), so a `HEAD`, `204` or `304` response, which has no body, is never over it. A cap of `0` admits only an empty body. The header block is not the body and is not capped (see open points).

**`http.withconnectaddr(c;addr)`**: connect to `addr` instead of resolving the URL's host. `addr` must be an IPv4 or IPv6 address literal (`"203.0.113.7"`, `"2001:db8::7"`, with no brackets, port or zone). It is used with `AI_NUMERICHOST`, so nothing is looked up. The port is the URL's. The URL's host is still used everywhere else:

- it is the `Host` header;
- it is the SNI name, when it is a DNS name;
- it is the name the server's certificate must carry (the 138.8 / 135.25 verification is unchanged).

This mirrors `curl --resolve`. The address is checked when a request is made, not when the option is set, because `http.withconnectaddr` returns a client and has no error channel:

- an `addr` that is not an address literal is `$err` (`withconnectaddr: not an IPv4 or IPv6 address literal`);
- a client that has both a connect address and a proxy is `$err` (`withconnectaddr cannot be combined with withproxy`), because the proxy makes its own connection to the URL's host.

### 2. A header-carrying GET (138.27)

```text
f=http.getheaders(url:$str;headers:@(@($str))):$httpresp!$httperr
```

This is `http.postheaders` without a body, sent with method `GET`. It goes through the same client and is held to 138.8's rules:

- each header is an `@(name; value)` pair;
- `Host` and `Content-Length` are the client's, and giving either is `$err`;
- a name or value holding a carriage return or line feed is `$err`, and nothing is sent;
- over `https://` the certificate is verified;
- `$err` means only a transport failure: a status such as `404` is a response, returned in `r.status`.

No `Content-Type` is added. Like `http.postheaders`, it takes a URL, not a client, so the controls in §1 do not apply to it. A caller that needs both uses a client call (open points).

### 3. A resolver (138.25)

```text
t=$neterr{msg:$str;code:u64}
f=net.resolve(name:$str):@($str)!$neterr
```

`net.resolve` returns every address `name` resolves to, A and AAAA records alike. Each address appears once, as a numeric string (`"127.0.0.1"`, `"::1"`), in the order the system resolver returned them. It makes one `getaddrinfo` call of any family. It does not set `AI_ADDRCONFIG`, so the caller gets the addresses the name has, not only those this host could reach today. An address literal resolves to itself.

A name that does not resolve, and an empty name, is `$err`. `msg` reads `net.resolve: <name>: <resolver message>` (or `net.resolve: empty name`), and `code` is 0.

The call requires the **`net`** capability, as connect does. A program without the grant stops with `CAP001`, the same as at every other `TK_REQUIRE` site. `getaddrinfo` is already a net primitive to `scripts/check_capability_sinks.py`.

`$neterr` has the shape of `$httperr` (`msg`, `code`), so code that handles one network error handles the other. `code` 0 marks a failure that has no number of its own, as it does for `$httperr`'s transport failures.

**The pattern these support** (loke's `packages/moke/tests/test_proxy_fetch.tk`): resolve the name, refuse the fetch if any address fails the caller's rules, then fetch with `http.withconnectaddr(c;<the checked address>)`, a deadline and a cap. The connection goes to the address that was checked, and the certificate is still verified against the URL's name.

### 4. The `timeoutms` documentation (138.34)

`$httpclient.timeoutms` is a per-read timeout. It is the time allowed for each wait for data, and it restarts whenever data arrives. It is not a per-request timeout. `docs/stdlib/http.md` and the `stdlib-signatures.md` comment now say so, and point to `http.withdeadline` for a bound on the whole request.

## Naming choices

The owner's answers name `connectaddr`, `net.resolve` and `http.getheaders`. The rest of the naming was left to this amendment, and every choice below is the conservative one:

| Choice | Why |
|---|---|
| `http.withdeadline`, `http.withmaxbody` | The existing option style (`http.withproxy`). The 2026-11-13 re-check proposed these names. |
| `http.withconnectaddr` | The owner's `connectaddr`, in the same `with` style. The re-check's shorter `withaddr` was not what the owner answered. |
| `u64` for `ms` and `bytes` | As `timeoutms` and `poolsize` are typed. |
| No "off" value; `0` is a real limit | A value that silently meant "no limit" would turn a cap computed as `0` into no cap at all. |
| `$neterr{msg;code}` | The shape of `$httperr`, the error type of std's other network client. The register's recommendation named `neterr` and left its shape open. |
| `@($str)` | The spec's notation for `[str]`. The register's `[str]` is the `.tki` spelling of the same type. |
| `http.stream` / `http.downloadfile` refuse the controls | They were not decided. Refusing is the safe default until they are. |

## Open points (not decided here)

- **The header block is not capped.** A server can still send an endless header block. The deadline bounds that in time, but memory is bounded only by how fast the server sends and how long the deadline is. Capping the header block is a separate decision, filed as story 138.49.
- **`http.stream` and `http.downloadfile`** refuse the controls instead of applying them. Applying them is a later change.
- **The URL-taking calls** (`http.geturl`, `http.postheaders`, `http.getheaders`) take no client, so they cannot carry the controls. The 2026-11-13 re-check proposed a client option for headers (`http.withheaders`). The owner chose `http.getheaders`, which is what is implemented. A client call with caller headers would need its own decision.
- **Host-name lookups are not interrupted by the deadline** (`getaddrinfo` blocks). Use `net.resolve` with `http.withconnectaddr` when that matters.
- **Defaults** (a default deadline or cap) are revisited at the next major, per the owner's answer.
