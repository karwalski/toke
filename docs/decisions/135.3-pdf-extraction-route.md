**Date:** 2026-09-23
**Status:** decided — a purpose-built C99 extractor
**Story:** 135.3 (Epic 135), gated by [ADR-0015](/docs/decisions/ADR-0015/)
**Written before the implementation**, so the reasoning survives independently of whether the implementation turned out well.

## What is being decided

ADR-0015 settled what `std.pdf` may **not** be: pdfium and podofo are disqualified as vendored dependencies because the toolchain is C99 only. It deliberately left the remaining choice to this story. The candidates that actually remain are:

- **A — vendor a full PDF engine** (MuPDF is the only one worth costing; see below for why poppler, pdfium and podofo do not get this far).
- **B — bind a full engine out-of-tree** through ADR-0015's escape hatch 1: `dlopen` a system-installed library behind a C shim.
- **C — write the minimal extractor.** Parse the cross-reference, inflate Flate streams, walk the content stream for the text-showing operators, apply the font's encoding map. No rendering, no rasteriser, no glyph outlines.

**C is chosen.** The reasoning below is mostly about why A and B are worse than they look, because "just use a library" is the answer that sounds responsible.

## The candidate libraries, and why only one survives to be costed

| Library | Language | Licence | Verdict |
|---|---|---|---|
| pdfium | C++ | BSD-3 | Disqualified by ADR-0015 (C++). |
| podofo | C++ | LGPL-2.0+ | Disqualified by ADR-0015 (C++). |
| poppler | C++ | GPL-2.0+ | Disqualified twice: C++, **and** GPL against this repository's Apache-2.0. |
| MuPDF | C (mostly) | **AGPL-3.0-or-later**, or commercial | The only one left to cost. |
| *a permissively-licensed C99 PDF text extractor* | — | — | **There isn't one of adequate quality.** |

That last row is the important one. ADR-0015's stated preference is "find or write a C equivalent" — the route that produced cmark, tomlc99 and miniz. For PDF, the *find* half of that sentence comes up empty: the mature extractors are pdf.js (JavaScript), pdfminer/pypdf (Python), PDFBox (Java) and the C++ four above. So the ADR's preferred route collapses to its second word, *write*, which is option C.

## Option A — vendor MuPDF

**Cost 1: licence. This is decisive on its own.** MuPDF is AGPL-3.0-or-later. This repository is Apache-2.0 (`LICENSE`, verified). Vendoring MuPDF into the default build would relicense every toke binary under the AGPL and attach a network-service source-disclosure obligation to every program a user compiles with `tkc` — because the stdlib is statically linked into the user's program, not merely into the compiler. That is a licence change imposed on every toke user in order to read a bank statement. It is not a trade that is ours to make, and no amount of engineering merit on MuPDF's side changes it. Artifex's commercial licence exists precisely for this case and costs money per shipped product.

**Cost 2: it is not actually all C.** MuPDF's `thirdparty/` tree includes HarfBuzz, which is C++. So vendoring MuPDF does not merely add ~500k lines of source; it adds the C++ toolchain requirement that ADR-0015 exists to refuse. (Stated from knowledge of MuPDF's layout, not verified in this worktree — but the licence cost above is sufficient without it, and is verifiable from the repository's own `LICENSE`.)

**Cost 3: size and maintenance surface.** MuPDF plus its thirdparty set (freetype, jbig2dec, openjpeg, lcms2, harfbuzz, libjpeg, zlib) is two orders of magnitude more code than the subset this story needs, essentially all of it serving rendering — rasterisation, colour management, JPEG2000, font hinting — which text extraction does not use. Every line of it is a line this project has to carry, security-patch and cross-compile.

**What A would genuinely buy.** This is real and should not be waved away: correct handling of the cases the minimal extractor will get wrong — embedded CID fonts with no `ToUnicode`, damaged cross-reference tables, exotic filters, and decryption of the empty-user-password documents. Those are the long tail. They are not the bank statement.

## Option B — `dlopen` a system MuPDF behind a C shim

The build stays C99 and nothing is vendored, so ADR-0015 is satisfied. But:

- **The licence cost does not go away for the user.** Dynamic linking against an AGPL library is still combination; a user shipping a toke binary that loads `libmupdf` inherits the obligation. We would be handing users a licence hazard with a friendly API on it.
- **The capability is absent on almost every machine.** `libmupdf` is not installed by default anywhere. So the honest description of B is "`std.pdf` returns `$unsupported` on a default macOS or Linux box", which is close to not shipping the capability.
- **It still needs all of option C's surface anyway**, minus the parser: positions, run splitting, the toke-side types, caps and tests.

B is the right route for a capability where the library is ubiquitous and permissive. Neither is true here.

## Option C — the minimal extractor, costed by component

The required subset is much smaller than a renderer because everything about *drawing* is out of scope. What is actually needed, with what each part buys and what it will get wrong:

| Component | Est. C99 | What it buys | What it will get wrong |
|---|---|---|---|
| Object lexer + parser (dict, array, name, number, string, ref, stream) | ~350 | Everything else depends on it | Nothing structural; PDF's object syntax is small |
| Cross-reference: classic table, xref streams, `/ObjStm`, plus a brute-force recovery scan | ~350 | Finds objects in files from every producer since 1993 | Multiply-updated files where the newest generation is not the last in file order |
| Flate via **zlib** + PNG predictors | ~150 | Every compressed stream. **Adds no dependency**: `LDLIBS` is already `-lm -lz -lpthread` (`Makefile:68`) | LZW, JBIG2, CCITT — not used for content streams in practice |
| Page tree walk, `/MediaBox`, `/Resources`, `/Contents` | ~200 | Page count, per-page access, coordinates | Inherited attributes on deeply pathological trees |
| Content-stream interpreter: `q/Q/cm/BT/ET/Tm/Td/TD/T*/TL/Tf/Tc/Tw/Tz/Ts/Tj/TJ/'/"` | ~400 | **The positions.** This is the part that makes tabular extraction possible | Rotated/skewed text reports width along the baseline, not an axis-aligned box |
| Font metrics: `/Widths`, `/W`+`/DW`, built-in standard-14 tables | ~250 | Correct run widths, hence correct boxes | Fonts with neither `/Widths` nor a standard-14 name fall back to 0.5 em |
| Encoding → Unicode: `ToUnicode` CMap, `/Differences`, WinAnsi/MacRoman/Standard | ~450 | Correct **text**, ligatures included | CID fonts with no `ToUnicode`: no mapping exists to be right about |
| Encryption detection | ~30 | Priority 3, as a distinct error | Does not decrypt, deliberately |
| Doc/page API, caps, error plumbing | ~250 | — | — |
| Glue + `.tki` + docs + C032 | ~1,100 | — | — |

**Estimated ~2,400 lines of C plus ~1,100 of interface, docs and test.** That is comparable to `std.xlsx` (1,492 + 656) and an order of magnitude below any of the libraries — and unlike them, every line is a line this project chose, in the language the build already speaks, under the licence the project already has.

**The honest weakness of C** is the same one option A would fix, and it is worth naming rather than discovering later: *font encoding is where a minimal extractor produces plausible wrong output.* A document whose text is an embedded subset font with no `ToUnicode` map contains no information about what its glyph codes mean — a full renderer does no better on such a file except by heuristics. The defence adopted here is not to be cleverer but to be **loud**: an unmappable code is emitted as U+FFFD, so the failure is visible in the output rather than plausible.

## Scope call, made now rather than discovered at the end

The story lists five items in priority order and says explicitly that a complete subset beats a broken whole. **Items 1–4 are implemented completely; item 5, embedded image extraction, is not implemented.**

Image extraction is a different problem wearing the same file format: it needs DCTDecode/JPXDecode/CCITTFaxDecode passthrough and a decision about what a toke-side image handle even is, and it shares nothing with the text path but the object parser. Half of it would be worse than none. It is left for its own story, where it belongs next to `std.image`.

What ships: text runs with positions (1), page count and per-page access (2), encrypted-PDF detection as a distinct error (3), and the `hastext` scanned-document signal (4).

## Consequences

- `std.pdf` links nothing new. zlib was already on the link line for every toke binary.
- miniz is **not** used here. It is `#include`d directly into `src/stdlib/zip.c` as a single translation unit with `MINIZ_NO_DEFLATE_APIS` set locally, so a second consumer including it again would be a second copy of those symbols. zlib is the right dependency for this module and is already present.
- `std.pdf` has no module dependencies: unlike `std.xlsx`, a PDF is not a zip.
- If a real input ever demands the long tail — CID fonts without `ToUnicode`, decryption, damaged files — the route to reopen is option B under a permissive engine, or a separate optional component under ADR-0015's hatch 2, not an amendment that vendors AGPL code.
