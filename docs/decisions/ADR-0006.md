> **Implementation note (2026-06-30).** Shipped D2 with one refinement: rather
> than a runtime `retain` at every array-typed handle copy (risky, because
> `expr_llvm_type` cannot distinguish an array from a string/struct and a
> mis-targeted `retain` would corrupt the wrong block), uniqueness is proven
> **statically** by a conservative per-function linear-array analysis. The
> in-place fast path fires only for `x = x.append/set(...)` where `x` is shown
> never to be aliased. The `rc`/`cap` header is in place; the eventual D1
> follow-up (release/free) can build on `rc` directly. conform 180/0; value
> semantics verified by `test/standalone/test_array_inplace.tk`.

## Context

toke arrays are **value-semantic and immutable in place**. Every mutating
operation allocates a fresh backing block and copies:

```c
/* collections_glue.c / str_glue.c — current ops, ALL O(N) per call */
tk_array_append_w : malloc(len+2) ; memcpy(len) ; write ; return new   // O(N)
tk_array_set_w    : malloc(len+1) ; memcpy(len) ; write ; return new   // O(N)
tk_array_pop_w    : malloc(len)   ; memcpy(len-1)        ; return new   // O(N)
```

So building or updating an array incrementally is **O(N²)**:

```
let a = mut.@();
lp(i=0; i<N; i=i+1){ a = a.append(x) }   (* N appends × O(N) copy = O(N²) *)
```

Measured: ~300k `.set` on a 10k array ≈ 5 s. This **hard-blocks** two
algorithmically-correct corpus programs:

- **scrypt N=16384** (CRY-017) — the large ROMix array.
- **P-256 scalar multiplication** (MSG-006) — times out.

Small-array crypto (AES/ChaCha/bignum, fixed ≤ a few hundred words) is
unaffected.

### Why it is not a one-line patch

A bare in-place `set`/`append` is **unsafe** because assignment shares the
backing block:

```
let a = @(1;2;3);
let b = a;          (* copies the i64 HANDLE — no data copy; a and b alias *)
a = a.set(0; 9);    (* if this mutated in place, b would change too — WRONG *)
```

The value-semantics contract requires that `b` is unaffected. Any in-place
mutation must therefore be applied **only when the array is provably the sole
reference** to its block.

### Scope surprise: the header layout is baked into two layers

The current layout is `block[0] = len`, `handle = block + 1` (so
`handle[-1] == len`). This is hard-coded in **both**:

1. **The C runtime** — every `tk_array_*_w` in `collections_glue.c`,
   `str_glue.c`, plus `tk_arr_map/filter/reduce/sort` and the `tk_map_*`
   helpers (`malloc(len+1)`, `block[0]=len`, `block+1`, `ptr[-1]`).
2. **The emitted IR** — codegen reads the header *inline*, not only through
   runtime calls (`src/llvm.c`):
   - `.len` / `.len()` → `getelementptr i64, i64* %p, i32 -1` + load (≈2910, 3574)
   - `NODE_ARRAY_LIT` → `alloca [len+1]`, store len at `[0]`, data at `[1..]`,
     return `&data[0]` so `ptr[-1] == len` (≈4024–4145)
   - `NODE_INDEX_EXPR` → GEP `handle[i]` + load (≈3624)
   - array-literal spread/concat reads `base.len` from `ptr[-1]` (≈4061)
   - `docs/runtime-abi.md §4` documents this layout as the ABI contract.

**Any change to the header must update both layers in lockstep**, and the IR
sites are the easy ones to miss.

## Options considered

### D1 — Swift-style reference-counted copy-on-write (retain **and** release)

Header carries a refcount; `retain` (rc++) on every handle duplication,
`release` (rc--, free at 0) on every scope exit / overwrite. Mutation copies
iff `rc > 1`, else mutates in place. Fully transparent value semantics **and**
frees memory.

- ✅ The gold standard (Swift `Array`, Roc, Koka/Perceus). Correct and general;
  also fixes toke's current leak-everything model.
- ❌ Largest change. toke has **no automatic memory management today** (arrays
  are malloc'd and never freed). Introducing `release`+`free` means lifetime
  tracking at every bind/assign/param/return/scope-exit/closure-capture — a
  use-after-free minefield that must land perfectly or it corrupts memory.
  High risk against the conform-180/0 gate.

### D2 — Capacity + **monotonic**-refcount copy-on-write (retain only, never free) ★ recommended

Header gains `cap` and `rc`. `retain` (rc++) on handle duplication; **no
release, no free** (keep today's leak-forever model). Mutation:

```
if rc == 1:  mutate in place   (append: use spare cap, else double-grow once)
else:        copy to a fresh rc=1 block   (value semantics preserved)
```

- ✅ **Cannot introduce use-after-free** — nothing is ever freed; the only
  failure mode of an over-count is an unnecessary copy (slower, never wrong).
- ✅ **Solves the actual blocker.** The hot loops (`a = a.append(x)`,
  `a = a.set(i;v)` with no alias) keep `rc == 1`, so they mutate in place →
  O(N) total, amortized O(1) per op. scrypt/P-256 build at full speed.
- ✅ Preserves value semantics: a genuinely-aliased array has `rc > 1`, so the
  mutation copies and the alias is untouched.
- ✅ No language-surface change; existing programs keep working unchanged.
- ⚠️ Correctness of the in-place path depends on the `retain` being emitted at
  **every** array-typed copy site. Miss one and two live references both see
  `rc == 1` → in-place mutation corrupts the alias. Mitigation below.
- ⚠️ `retain` must be **type-directed** (only rc++ a value known to be an
  array/`[byte]`/map). toke has known element-type erasure (113.B.10/114.16),
  so a copy site mistyped as non-array would skip `retain`. Mitigation: at a
  copy site of *unknown/erased* type, fall back to the safe path — treat the
  source as shared (force-copy on its next mutation) rather than risk a missed
  retain. Over-copying is safe; a missed retain is not.

### D3 — Explicit mutable builder type (`vec`/`buf`), value arrays stay immutable

Add a distinct **reference-semantic** growable type with genuine O(1) in-place
`push`/`set`, separate from value arrays. Crypto builds into a `vec`, then
`.freeze()`s to an array.

- ✅ Lowest risk to **existing** semantics — value arrays are untouched, so
  conform cannot regress on array behaviour. No retain/release, no aliasing
  ambiguity (a `vec` is openly a reference).
- ✅ Ships the crypto unblock soonest and in isolation.
- ❌ A language addition (new type + ops + `.tki`), and crypto programs must be
  **rewritten** to use it. Ergonomically it is the Rust/C++ `Vec` model rather
  than the functional value-array model toke currently presents — a philosophy
  split between two array-like types.

## Recommendation

**Adopt D2** (capacity + monotonic-refcount CoW) as the principled,
bounded fix:

- It is the value-semantic-preserving design consistent with toke's functional
  array model (the same family as Swift/Roc), so it is the "do it right" answer
  rather than a workaround.
- The monotonic (retain-only) variant removes the single scariest part of D1 —
  freeing — so it **cannot cause memory corruption**; its worst case is a
  redundant copy. That makes it tractable under the conform-180/0 gate.
- It needs no language-surface change and leaves every existing program valid.
- D1 (add `release`+`free`) becomes a clean **follow-up** once D2's refcount
  infrastructure is proven — flip the leak model to reclaiming memory later,
  separately, behind its own gate.
- D3 remains the fallback if, during step 2 below, the `retain`-coverage audit
  shows the array-typed copy sites cannot be enumerated reliably given current
  type erasure — in that case ship the explicit `vec` builder instead.

## Implementation plan (D2, conform-gated at every step)

Header redesign (keep `len` reachable at a fixed negative offset to minimize IR
churn):

```
[ rc | cap | len | data[0] | data[1] | ... ]
        handle ──────────────^   (handle[-1]=len, handle[-2]=cap, handle[-3]=rc)
```

1. **Header + runtime ops.** Introduce `tk_array_alloc(cap)` /
   `tk_array_header` helpers; rewrite every `tk_array_*_w` and
   `tk_arr_*`/`tk_map_*` in `collections_glue.c` + `str_glue.c` to the
   3-word header. `append`/`set`/`pop` branch on `rc`: in-place when `rc==1`
   (append grows `cap` by doubling only when `len==cap`), copy otherwise.
   `runtime-abi.md §4` updated. **Gate: `make conform` 180/0.**
2. **`retain` coverage audit + insertion (`src/llvm.c`).** Enumerate every site
   that duplicates an array-typed value: `let`/`=` binds, assignment,
   call-argument pass, `return`, store into struct field / array element,
   closure capture. Emit `call @tk_array_retain(i64 %h)` (type-directed; no-op
   on rc for non-array). At unknown/erased-type copy sites, mark the source
   force-shared. **Gate: conform 180/0 + a value-semantics test
   (`let b=a; a=a.set(0;9); assert b[0] unchanged`).**
3. **Inline-IR header reads.** Update the codegen sites that read the header
   directly (`.len` GEP `-1` stays valid; `NODE_ARRAY_LIT` alloca must reserve
   the 3 header words and init `rc=1,cap=len,len`; spread/concat len reads).
   **Gate: conform 180/0.**
4. **Mutation fast-path verification.** Microbenchmark the `a=a.append/set`
   loop: confirm O(N) (not O(N²)) — the 10k×300k case drops from ~5 s to
   sub-second.
5. **Crypto KAT.** Re-enable scrypt N=16384 (CRY-017) and P-256 scalar-mul
   (MSG-006); verify against known-answer vectors and that they complete in
   time. **Gate: conform 180/0; corpus delta ≥ 0.**
6. **(Follow-up, separate ADR/story)** D1: add `release`+`free` to reclaim
   memory, converting the leak-forever model to reference-counted reclamation.

## Verification

- `make conform` stays **180 passed, 0 failed** after every step (non-negotiable).
- Value-semantics regression test: aliased array unaffected by a mutation of the
  original (the core correctness property of CoW).
- Microbenchmark: incremental build/update is O(N), confirmed by timing at
  N ∈ {1k, 10k, 100k}.
- scrypt N=16384 and P-256 scalar-mul produce correct KAT outputs within time.
- Regression sweep over struct/array-heavy corpus programs (the `retain`
  insertion touches array-typed binds — confirm no behavioural change).

## Risks & mitigations

| Risk | Mitigation |
|---|---|
| Missed `retain` at a copy site → alias corruption | Type-directed insertion + **force-shared fallback** at unknown/erased-type sites (over-copy is safe; missed retain is not). Dedicated value-semantics test in conform. |
| Type erasure (113.B.10/114.16) mistypes an array copy as scalar → skips retain | Same fallback: erased type ⇒ treat as shared. Never rc++ a value not known to be an array (would corrupt an integer). |
| Header change desyncs runtime vs inline IR | Single source of truth for offsets (`#define TK_ARR_HDR 3`); update `runtime-abi.md` and both layers in the same step; conform-gate. |
| Monotonic rc defeats CoW for long-lived shared arrays | Acceptable — those are not the hot path; they merely copy as today. The blocker (unaliased loop-building) is fully solved. |
| Scope creep into a GC | Explicitly **out of scope**: D2 keeps leak-forever; reclamation (D1) is a gated follow-up. |
