## Context

The Epic 120 audit found that toke's std library and the ooke app framework are
**injection-safe only if the developer opts in**, and unsafe by default on the three
highest-leverage surfaces. That is the wrong polarity for a language whose pitch is
"safe, verifiable, LLM-authored code": an LLM (or a human) that writes the *obvious*
call gets the *unsafe* behaviour. The concrete findings this ADR responds to:

- **Command execution.** `std.process` already ships a safe argv-only export —
  `process.spawn([str])` decodes the array and calls `execvp` directly, no shell
  (src/stdlib/process_glue.c:29). But three convenience wrappers that are **not** in
  `stdlib/process.tki` — `process.exec`, `process.readlines`, `process.spawndetached`
  — route a single command **string** through `sh -c` via `spawn_shell`
  (process_glue.c:18, findings AMB-02). `process.spawn` also trusts `$PATH` for
  `argv[0]` while `$PATH` is program-writable (AMB-03). `server_ops` already execs via
  `execv(bin, argv)` (server_ops.c:153) — no shell — but inherits a socket fd whose
  number comes from `$TK_LISTEN_FD` (AMB-10). There is today **no stated guarantee**
  that std exec is shell-free, so the shell wrappers read as blessed API.
- **Template output.** The C engine's public `tpl.render` maps to `tmpl_render`, which
  calls `render_internal(..., escape_values=0)` — **no HTML escaping**
  (template.c:906). An escaping path (`tmpl_renderhtml`, escape_values=1) exists in C
  but is **not exported** in `stdlib/template.tki`; escaping is only reachable by the
  developer manually calling `tpl.escape`. ooke's own engine is worse: `{=x=}` emits
  **raw**, and HTML escaping is an opt-in `|escape` filter (template.tk / serve.tk,
  findings OOK-02, OOK-06). The live site is therefore **XSS-by-default**. `md_render`
  compounds this by forcing `CMARK_OPT_UNSAFE` (PAR-05).
- **SQL.** The parameterized path **already exists and is the primary API**:
  `db.one/many/exec` take `(str, [str])` (stdlib/db.tki). The injection comes from the
  *other* paths kept alongside it — the string-concatenating query-builder wrappers
  (`tk_db_buildinsert_w` etc. concatenate values into a fixed 4096-byte buffer,
  DAT-01/DAT-05), the legacy raw-SQL wrapper `tk_db_query_w` that takes a pre-built
  string with empty params (DAT-02), the **MySQL backend that silently discards bound
  parameters** so `?` placeholders send literally (DAT-03), and ooke's `store.tk`
  concatenating table/column identifiers (OOK-04). So the guarantee is undermined by
  (i) unsafe sibling APIs and (ii) a backend that doesn't honour the safe one.

The common thread: **the safe primitive usually exists; the unsafe one is reachable by
default or by an equally-prominent alternate.** The fix is to make the safe form the
*only* form (or the default), not to add more escaping helpers.

## Decision

Adopt an **injection-proof-by-construction** posture across the three surfaces. Each
sub-decision names a recommended option; all three are independent and can be ratified
separately.

### (a) `std.process` / `server_ops`: argv-only guarantee, shell forms removed

**Recommend A2.** Make it a *language-level, documented guarantee* that no std API ever
invokes a shell, and delete the string-command wrappers.

- **Guarantee (normative, add to `runtime-abi.md` + `std.process` docs):** *"No
  function in `std.process` or `server_ops` passes its arguments to a shell. Every
  child process is created by `execv`/`execvp` from an explicit argument vector. There
  is no `system()`/`popen()`/`sh -c` path in the standard library."*
- **API shape:**
  - Keep `process.spawn(cmd:[str])` as the sole spawn primitive (already argv-only).
  - **Remove** the string wrappers `process.exec`, `process.readlines`,
    `process.spawndetached` in their current shape (they take a single command
    *string* and call `sh -c`). Re-provide the *ergonomics* on an argv basis:
    - `process.run(cmd:[str]) -> RunResult!ProcessErr` — spawn+wait+capture stdout
      (the safe replacement for `exec`).
    - `process.lines(cmd:[str]) -> [str]!ProcessErr` — `run` then split (replaces
      `readlines`).
    - `process.detach(cmd:[str]) -> bool` (replaces `spawndetached`).
    - None accept a shell string. A developer who genuinely wants a shell must write
      `process.spawn(@("sh"; "-c"; userScript))` **explicitly** — the shell becomes a
      visible, greppable, reviewable argv element, never an implicit default.
  - **`argv[0]` resolution (AMB-03):** `process.spawn` should `execv` an *absolute or
    explicitly-relative* path by default and only fall back to `$PATH` (`execvp`) when
    the caller passes a bare name **and** opts in (e.g. a `process.spawnpath(...)`
    variant), or resolve against a pinned `PATH` snapshot captured at process start.
  - **`server_ops` (AMB-10):** already shell-free; additionally require the inherited
    `TK_LISTEN_FD` to be validated (numeric, is a listening socket, CLOEXEC re-set
    after dup) rather than trusted verbatim. This is hardening, not an API change.
- **Rejected — A1 (keep wrappers, sanitise the string):** shell-string sanitisation is
  a perennial-CVE approach (quoting rules differ per shell, `$()`/backtick/newline
  edge cases); it contradicts "do it right." A3 (gate exec behind a capability token,
  cf. AMB-01) is **complementary** and recommended as a *follow-up* — even argv-only
  exec should ultimately require an explicit capability — but does not by itself remove
  the shell-injection surface, so A2 lands first.

### (b) Templates: auto-escaping by default, raw is explicit opt-out — in BOTH engines

**Recommend B1 (context-agnostic HTML-escape default now; typed contexts later).** Flip
both template engines so an interpolation is **HTML-escaped unless the author marks it
raw**.

- **C engine (`std.template`):**
  - Make `tpl.render` escape by default: point the `tpl.render` export at the
    `escape_values=1` path (`tmpl_renderhtml`) — i.e. `render_internal(..., 1)`.
  - Provide an explicit raw escape hatch, named to be unmistakable:
    `tpl.renderraw(t, vars)` (maps to the current `escape_values=0`). Raw is never the
    default and never the short name.
  - Per-slot opt-out at the template syntax level: `{{name}}` escapes; `{{name|raw}}`
    (or `{{&name}}`) emits raw. Keep `tpl.escape` for manual use but it is no longer
    load-bearing for safety.
- **ooke engine (`template.tk`):**
  - **Invert the `{=x=}` default:** `{=x=}` becomes **HTML-escaped**. Introduce an
    explicit raw form — `{=x|raw=}` (reusing the existing filter-pipe lexer already in
    `tplresolveexpr`) or a distinct `{=&x=}` — for the rare intentional-HTML case.
  - The router's path-parameter capture (OOK-06) is then safe when rendered through a
    slot, since slots escape by default.
- **Markdown (PAR-05):** stop forcing `CMARK_OPT_UNSAFE`; default `md_render` to the
  safe cmark mode and sanitise link hrefs, with an explicit `md.renderunsafe` (or an
  options flag) for trusted input only. Same polarity as the template decision.
- **Direction of travel (non-blocking):** the *correct* long-term design is
  **context-aware** auto-escaping (HTML-body vs attribute vs URL vs JS vs CSS), as in
  Go `html/template`. That is a larger build; B1 ships the high-value HTML-body default
  now and reserves context typing as a follow-up ADR. Escaping the wrong context (e.g.
  HTML-escaping inside a `<script>`) is still safer than today's raw default.
- **Rejected — B0 (keep opt-in, document loudly):** documentation does not change the
  default an LLM emits; this is exactly the failure mode the audit found live.

### (c) `db.*`: parameterized-query guarantee, no string-SQL alternative

**Recommend C1.** Make parameter binding the *only* way values enter a query, and make
identifiers a typed, validated construct rather than free string concatenation.

- **Guarantee (normative):** *"Values are only ever sent to the database as bound
  parameters. No `std.db` API interpolates a runtime value into SQL text. Every backend
  MUST transmit placeholders as real prepared-statement parameters."*
- **API shape:**
  - `db.one/many/exec(sql:str, params:[str])` stay as the canonical, and become the
    *only*, value-carrying entry points. `sql` is expected to be a compile-time-ish
    constant with `?`/`$n` placeholders; `params` carries all values.
  - **Remove** `db.query`/legacy `tk_db_query_w` (single pre-built SQL string, DAT-02)
    and the string-concatenating query-builder emitters (`buildinsert`/`buildwhere`,
    DAT-01/05). If a fluent builder is desired, it must produce **(sql-with-placeholders,
    params[])**, never a finished SQL string — the builder output is fed into
    `db.exec`, so escaping is structurally impossible to skip.
  - **Identifiers** (table/column names — the one thing you cannot parameterise):
    provide `db.ident(name) -> Ident` that validates against
    `^[A-Za-z_][A-Za-z0-9_]*$` (or a per-backend quoting rule) and is the *only* type
    accepted where an identifier is interpolated. This closes DAT-04 and ooke OOK-04
    (`store.tk` table/column concatenation) without banning dynamic table names
    outright.
  - **MySQL backend (DAT-03) is a correctness bug, not an API choice:** it currently
    accepts params and silently drops them, so `?` goes to the server literally — this
    *breaks* the guarantee for anyone who followed the safe API. Fix it to bind via
    `mysql_stmt_bind_param` (or reject the backend until it does). TLS enforcement
    (DAT-06) and not propagating raw driver error strings (DAT-07) ride along.
- **Rejected — C0 (keep raw wrappers, add an escaping helper):** an escaping helper is
  the classic footgun (wrong-quote, encoding, second-order injection); binding is the
  only construction the audit accepts.

### Cross-cutting

The dead in-runtime WAF (RUN-01: `security.c` is linked but never invoked) is **not**
the remedy for any of the above and must not be positioned as a compensating control.
Injection safety is delivered at the API boundary (this ADR); a WAF, if revived, is
defence-in-depth only and is tracked separately.

## API-shape summary

| Surface | Today (unsafe default) | Proposed default | Explicit opt-out |
|---|---|---|---|
| process | `process.exec(str)` → `sh -c` | `process.run([str])` argv-only; **no shell API** | `process.spawn(@("sh";"-c";s))` written by hand |
| template (C) | `tpl.render` = unescaped | `tpl.render` = HTML-escaped | `tpl.renderraw` / `{{name|raw}}` |
| template (ooke) | `{=x=}` = raw | `{=x=}` = HTML-escaped | `{=x|raw=}` |
| markdown | `CMARK_OPT_UNSAFE` forced | safe cmark + href sanitise | `md.renderunsafe` |
| db values | builder/raw string concat | `db.exec(sql, params)` only | (none — no string-SQL path) |
| db identifiers | string concat | `db.ident(name)` validated | — |

## Migration & compatibility impact

- **(a) process — breaking for callers of the string wrappers.** `process.exec/
  readlines/spawndetached` change signature from `str` to `[str]` (renamed to
  `run/lines/detach`). These wrappers are **not in `stdlib/process.tki`** today, so they
  are undocumented glue with a small blast radius; a compiler diagnostic on the old
  names ("`process.exec(str)` removed; use `process.run([str])`, or
  `process.spawn(@(\"sh\";\"-c\";cmd))` for an explicit shell") drives migration.
  `process.spawn` itself is unchanged for existing argv callers. `server_ops` API is
  unchanged (hardening only).
- **(b) templates — breaking, and deliberately so, because the break is the fix.** Any
  template that *relied on* raw output of HTML (intentional markup passed through a
  slot) will now be escaped and must add `|raw`/`renderraw`. This is the desired
  direction: the failure mode of the migration is "HTML shows up escaped in the page"
  (visible, harmless), not "script executes" (silent, exploitable). A one-shot codemod
  can flag every `{=...=}` / `tpl.render` site for author review. The live toke website
  (ooke) must be swept before this ships. `md_render` callers on trusted input opt into
  `renderunsafe`.
- **(c) db — mostly compatible, because the safe API already exists.** Programs already
  using `db.one/many/exec(sql, params)` are unaffected. Removal hits the
  string-concatenating builder and the legacy `db.query` wrapper; a diagnostic points
  them at parameterised `db.exec`. The **MySQL fix is strictly a bug fix** — no caller
  intentionally relies on parameters being dropped. `db.ident` is additive; ooke's
  `store.tk` must adopt it where it concatenates identifiers.
- **Docs/spec:** add the three normative guarantees to `runtime-abi.md` and the module
  reference; update ooke's template docs; note in the security posture doc that
  injection safety is an API-boundary property.

## Consequences

- The *obvious* call is the *safe* call on all three surfaces — the polarity an
  LLM-authored codebase needs. Unsafe behaviour becomes explicit, named, and greppable
  (`spawn(@("sh"...))`, `renderraw`, `renderunsafe`), so it is auditable rather than
  accidental.
- Several Epic 120 findings collapse to "resolved by design" rather than needing
  individual patches: AMB-02, OOK-02, OOK-06, PAR-05, DAT-01, DAT-02, DAT-04, OOK-04.
  The buffer-overflow findings that live in the *unsafe* paths being removed
  (DAT-05 builder overflow, PAR-05) disappear with the path.
- Cost is real breakage in template output and the process/db string forms; it is
  bounded (safe primitives already exist for spawn and db-params) and fails visibly.
- Follow-ups (separate ADRs/stories): capability-gated ambient authority (AMB-01),
  context-aware template escaping, reviving the WAF as defence-in-depth (RUN-01).

## Decision needed

Three independent ratifications: **(a)** remove shell-string process wrappers + publish
the argv-only guarantee; **(b)** flip both template engines to escape-by-default; **(c)**
make parameterised binding the only value path in `db.*` and fix the MySQL backend.
**Awaiting owner decision before any code is written.**
