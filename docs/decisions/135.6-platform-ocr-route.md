**Date:** 2026-09-23
**Status:** decided — bind macOS Vision from plain C99 through `objc_msgSend`
**Story:** 135.6 (Epic 135), gated by [ADR-0015](/docs/decisions/ADR-0015/)
**Written before the implementation**, and the measurements below were taken before the interface was designed, so the reasoning survives independently of whether the implementation turned out well.

## What was measured, on what

macOS **26.5.1** (build 25F80), arm64, SDK 26.5. Four standalone C99 probe programs, each compiled with

```
cc -std=c99 -Wall -Wextra -Wpedantic \
   -framework Vision -framework CoreGraphics -framework CoreText \
   -framework CoreFoundation -framework Foundation -lobjc
```

**No `.m` file, no `-x objective-c`, no C++ translation unit, no `CXX`.** The probes compiled with zero warnings under `-Wpedantic` and ran without triggering any macOS permission dialog.

## Finding 1 — the C99 route holds. ADR-0015 is not threatened.

`src/stdlib/webview.c` already binds WebKit and Cocoa this way, and Vision is no harder. Every call the binding needs is reachable:

| What | Reached how | Result |
|---|---|---|
| `VNImageRequestHandler` | `objc_getClass` | non-NULL |
| `VNRecognizeTextRequest` | `objc_getClass` | non-NULL |
| `-initWithCGImage:options:` | `class_respondsToSelector` | yes |
| `-performRequests:error:` | `class_respondsToSelector` | yes |
| `-setRecognitionLevel:` | `class_respondsToSelector` | yes |
| `-setRecognitionLanguages:` | `class_respondsToSelector` | yes |
| `+currentRevision` | metaclass | `3` |
| `+supportedRevisions` | metaclass | `NSIndexSet {1,2,3}` |
| `+supportedRecognitionLanguagesAndReturnError:` | instance | 30 languages |

Two ABI details make this work on arm64 and are worth writing down, because both are places where a wrong cast compiles and then returns nonsense:

- **`CGRect` comes back in registers.** There is no `objc_msgSend_stret` on arm64; a four-double struct is a homogeneous float aggregate and is returned directly. A `boundingBox` read through a plain `objc_msgSend` cast is correct here and would not be on i386.
- **`VNConfidence` is a `float`.** There is no `objc_msgSend_fpret` on arm64 either, so the plain cast is again correct.

`initWithCGImage:options:` takes a `CGImageRef`, which is a C type. The image never has to become an `NSImage`, so no AppKit, and the pixels never leave the process.

**Verdict: this story does not need a toolchain change.** One `.c` file, one `_glue.c`, and `-framework Vision -framework CoreGraphics -framework ImageIO -framework CoreFoundation -framework Foundation -lobjc` on the link line.

## Finding 2 — Vision's confidence carries no information on this OS

This is the finding that changes the story, so it is stated bluntly.

`VNRecognizedText.confidence` was sampled across 40 images: clean text, faint text (grey 0.70 to 0.95), 45% salt-and-pepper noise, rotations of 0/5/10/20/45/90 degrees, font sizes 5pt to 44pt, image widths 20px to 900px, and deliberately confusable glyph strings. At `VNRecognizeTextRequestRevision3` with `recognitionLevel = accurate`:

**Every recognised candidate returned `confidence == 1.0`. Without exception.**

Including these, which are wrong:

| Image contains | Vision returns | Confidence |
|---|---|---|
| `Illlll1I0O` | `\|\|\|\|\|1100` | **1.000000** |
| `ACME` at 6pt in 24x10px | `VOME` | **1.000000** |
| `ACME BANK` rotated 45 degrees | `= BANK` | **1.000000** |
| `ACME BANK` rotated 90 degrees | `ANK` | **1.000000** |
| `l1I\|` | `11ll` | **1.000000** |

At revision 2 a clean image scores 0.5 where revision 3 scores 1.0, for byte-identical input.

`recognitionLevel = fast` is the one place any variation was found, and it is worth stating precisely because the first version of this note overstated it. In the original 40-image sweep fast returned `0.5` for every candidate it returned at all. A later three-line fixture disproved "always 0.5": `ACME BANK` and `Balance 1,234.56 GBP` scored `0.5` while `Ref 998877`, in the same image, scored `1.0`. So fast-level confidence takes at least two values and may carry some signal. It is thin, it is not characterised, and nothing here is built on it — but the claim that it is constant is withdrawn.

**The load-bearing finding is about `accurate`, and it stands: across every sample at revision 3 / accurate, confidence was 1.0 — including on output that is flatly wrong.** Accurate is the default and the only level a statement-reading consumer would choose, so for the purpose that motivates this epic the number is a label for how the request was configured rather than a measurement of how the recognition went.

`-topCandidates:` compounds this. Asked for 3 or 5 alternatives, revision 3 returns **exactly one** candidate in every one of the 40 samples, so the usual fallback of "look at the margin between the top two candidates" is not available either.

### What this means for the story, and for 135.8

Story 135.6's brief says *"Vision returns a confidence; surface it. Do not average it away."* It does return one and this module surfaces it, unaveraged and per-run. But a consumer that flags a low-confidence field by testing `run.confidence < 0.9` **will never flag anything**, and the bank-statement consumer that motivates this epic is exactly that consumer.

Story 135.8's row makes per-glyph and per-field confidence load-bearing. **The platform binding cannot deliver it**, and no amount of care in this module changes that, because the number does not exist behind the API. If per-field confidence is genuinely required, that requirement is an argument *for* 135.8 rather than something 135.6 can defer — which is the opposite of what the row assumes when it says shipping this lets 135.8 wait.

### The signal that does exist

Vision refuses cleanly. Text below roughly 7pt in the sampled geometry, and everything at `fast` level that it cannot handle, produces **zero observations** rather than a wrong answer. Zero runs from a page that is visibly covered in text is real information, and it is the signal this module gives a consumer instead of a fake confidence gradient. `docs/stdlib/ocr.md` says so in those words, so that nobody builds a threshold on a constant.

## Finding 3 — an unrecognised selector is fatal, so every selector is probed

A C program has no `@try`. `-[NSIndexSet allObjects]` — a selector that does not exist, sent during probing — terminated the probe with an uncaught `NSInvalidArgumentException` and a stack trace. There is no recovery path from C.

The binding therefore sends **no selector it has not first confirmed** with `objc_getClass` and `class_respondsToSelector`, and `ocr.isavailable` performs exactly those checks plus a live call to `+supportedRecognitionLanguagesAndReturnError:`. That is also why `ocr.isavailable` is honest rather than a hard-coded constant: the checks it would need for safety are the same checks that answer the question.

## Why not Tesseract, and why not wait for 135.8

[ADR-0015](/docs/decisions/ADR-0015/) refuses vendoring Tesseract (story 135.7) — it is C++, and the C API is a wrapper over a C++ core, so the C++ translation units come with it either way. That leaves the platform recogniser or a standalone component.

Portability is poor by construction: a different engine per platform, and none on bare Linux. That is the accepted trade in the story row. The mitigation is the interface, not the implementation — see `docs/stdlib/ocr.md`. A caller asks for runs and gets runs; `ocr.engine()` names who produced them; `ocr.isavailable()` says whether anyone can. Nothing in the interface spells "Vision", so 135.8 can be added as a second engine behind the same calls.

## Why the record shape matches std.pdf's `$textrun` slot for slot

The consumer that motivates this epic routes on `pdf.hastext`: text pages go through `pdf.runs`, scanned pages through `ocr.runs`, and **both halves feed one field extractor**. If that extractor needs two record types, the interface has failed.

`$ocrrun` is therefore laid out as `$textrun` is, with the same names, types and order:

| Slot | `std.pdf` `$textrun` | `std.ocr` `$ocrrun` |
|---|---|---|
| 0 | `text` str | `text` str |
| 1 | `page` i64 | `page` i64 |
| 2 | `x` f64 | `x` f64 |
| 3 | `y` f64 | `y` f64 |
| 4 | `width` f64 | `width` f64 |
| 5 | `height` f64 | `height` f64 |
| 6 | `fontsize` f64 | **`confidence` f64** |

Six of seven slots are identical in name, type and position, and the seventh differs in name only — same type, same slot, same size. Under the runtime ABI (`docs/runtime-abi.md` §5, a struct is a flat i64 block, one slot per field in declaration order) the two records are **bit-identical in layout**, so converting between them is a re-tag and never a re-pack.

The seventh slot is the one real divergence, and it is the honest one: **a PDF knows the font size and not the confidence; a recogniser knows the confidence and not the font size.** The rejected alternative was to keep `fontsize` and always write `0.0` into it, which preserves the name at the cost of shipping a field that is a lie in every row, and which somebody eventually divides by.

**Coordinates follow std.pdf, not the raster convention**: origin bottom-left, y increasing upward. Vision's normalised `boundingBox` already uses that origin, so only the unit is converted — normalised 0..1 becomes **pixels of the source image**, because pixels are the only unit an image has. A consumer that already sorts `$textrun`s into reading order sorts `$ocrrun`s with the identical comparison, which is the whole point.

## What is deliberately not here

- **Per-glyph boxes.** `-boundingBoxForRange:error:` exists, but with one candidate and a constant confidence it would return geometry nobody can act on. Story 135.8.
- **Document structure**, tables, reading-order reconstruction across columns. `ocr.text` joins observations in Vision's order and nothing more.
- **Windows.** The row names the Windows OCR API. It is stubbed to `$noengine` and named in the interface, not implemented — this machine cannot test it, and an untested platform branch that returns plausible values is the defect class this epic keeps finding.
- **Bare Linux.** There is no system recogniser. `ocr.isavailable()` is false and every call returns `$noengine`.
