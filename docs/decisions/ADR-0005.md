## Context

ooke is the reference web framework / CMS for toke ("toke on ooke"). Its
application source (`src/*.tk`) is already written entirely in toke, but the
framework only works because it links against the toke stdlib's C backing
layer (~58k lines of hand-written C across `src/stdlib/*.c` plus ~21k lines of
vendored C — `cmark` for Markdown, `tomlc99` for TOML). Every primitive ooke
needs — HTTP server, routing, TLS, crypto, Markdown, TOML, JSON, WebSocket,
file I/O — is C reached through the toke FFI/`extern` mechanism and exposed via
stdlib wrappers (`tk_*_w`) and `.tki` interfaces.

Two things were conflated in earlier framings of "rebuild ooke with no C glue":

1. Whether ooke should contain or reach C **directly**.
2. Whether the toke ecosystem should eliminate C **entirely** (down to syscalls).

These are different questions with very different scope. This ADR settles the
intent.

## Decision

**ooke contains zero non-toke code and never reaches a native symbol directly.
Any native capability ooke requires is implemented once in the toke project as
a reusable core/stdlib capability and consumed by ooke only through the
published toke API (module import → `.tki` interface → `tk_*_w` wrapper).**

Concretely:

1. **ooke is 100% toke.** No C, shell, Python, or hand-written JavaScript in the
   ooke repository. ooke never declares an `extern` function and never links a
   raw C symbol of its own.
2. **The C boundary is allowed — but it lives in toke core, not in ooke.** When
   a gap is found, the fix is a *generalised, reusable* toke stdlib capability
   (module + `.tki` + `tk_*_w` wrapper, C-backed where a true primitive is
   needed), so **every** toke program benefits, not just ooke. Glue is never
   ooke-shaped or app-private.
3. **ooke is the forcing function for toke-core completeness.** Each capability
   gap, missing library, runtime bug, or compiler limitation surfaced during the
   ooke rebuild becomes a story in `docs/progress.md` and is solved in toke
   core. ooke proves toke is a self-sufficient platform; loke then validates the
   result end-to-end, so plumbing parity with the current ooke is mandatory.
4. **Honour toke's design goals in the rebuild.** Small, multiple files; single
   canonical patterns; token efficiency. No mega-files.
5. **Companion-file and verification discipline.** Every `.tk` source file ships
   a `.tkc.md` companion per the Companion File Format Specification. The spec
   and syntax are consulted while authoring, and **each function is tested as it
   is written** (tests live in `test/`, run via `make test`).

This is *not* a commitment to eliminate C from toke entirely (no syscall-only,
libc-free runtime is required). C-backed stdlib in toke core is acceptable and
expected. The invariant is purely about *where* native code lives and *how*
ooke consumes it.

## Consequences

- ooke becomes a clean, pure-toke consumer of a deliberately growing toke stdlib
  surface. The published API (the `.tki` files) is the contract.
- The bulk of the engineering work may land in the **toke** repo (new/extended
  stdlib capabilities, wrappers, and compiler fixes), not in ooke — tracked as a
  paired story structure (see Epic 113).
- Capabilities added for ooke (e.g. richer HTTP, TLS config, Markdown, TOML,
  store backends) immediately benefit loke, moke, the website, and any
  third-party toke program.
- Security-sensitive primitives (TLS, crypto) remain C-backed in toke core for
  now; reimplementing them in pure toke is explicitly out of scope for this
  effort and is not required by "no C in ooke".
- The rebuild lives in a separate repo/folder (`toke-ooke-pure/`) seeded from
  the current ooke as the parity reference, on `feature/pure-toke-rebuild`,
  until it reaches parity and can replace `toke-ooke`.
