> This ADR proposes a direction; it does **not** ratify one. The choice between
> options B and C changes the language's security posture, its marketing story
> ("secure by default"), and the migration burden on every existing program.
> That is an owner call. The recommendation below is the reviewer's, offered to
> be argued with.

## Context

toke is AOT-compiled to native machine code with **no language-level sandbox and
no capability model**. Any program that imports `std.os`, `std.file`,
`std.env`, or `std.process` runs with the **full ambient OS authority** of the
invoking user — the only enforcement is the kernel's discretionary access
control for that uid. This is the headline design gap raised as **AMB-01** in
the 120.11 ambient-authority audit:

- `std.os` exposes raw `open`/`read`/`write`/`lseek`/`stat`/`unlink`/`rename`/
  `mkdir`/`rmdir`/`access`/`getenv`/`setenv`/`_exit` (`src/stdlib/os.c:23`).
- `std.file` adds arbitrary read/write/append/delete, recursive directory
  removal, copy/move, glob, and recursive listing (`src/stdlib/file.c`).
- `std.env` adds full read/write/delete/list of the process environment plus
  dotenv loading (`src/stdlib/env.c`).
- `std.process` adds fork+exec of arbitrary programs, including a
  `/bin/sh -c` string form (`src/stdlib/process_glue.c:18`,
  `src/stdlib/process.c:131`).

None of these consult any allowlist, root-jail, or grant token. The practical
consequences the audit confirmed:

- **No way to run untrusted or semi-trusted toke code.** Any dependency —
  transitively — or any ooke request handler that reaches a std API can read
  `~/.ssh`, exfiltrate secrets, delete files outside its tree, or spawn
  processes.
- **No privilege drop per request.** An ooke web author cannot confine a request
  handler; a template or parser bug becomes host-level compromise.
- **The ambient surface amplifies every injection finding.** Shell-string exec
  (AMB-02), PATH-trusting `execvp` (AMB-03), unrestricted dotenv `setenv` of
  `LD_PRELOAD`/`PATH` (AMB-04), symlink-following recursive delete (AMB-05),
  and non-normalizing `path_join` (AMB-06) are each individually exploitable,
  but they are dangerous *because* the ambient baseline means a single reached
  sink yields full user authority. The same ambient model is what turns the
  build-time toolchain injections (120.2 COM-01/COM-02, command injection via
  filename/`--out`/`--target` and `TKC_STDLIB_DIR`/`TKC_RUNTIME_DIR`) into
  host-level risk during compilation.

This directly contradicts toke's stated positioning. [ADR-0001](/docs/decisions/ADR-0001/)
frames toke as a language **designed for machine generation** — code produced by
an LLM and run in an automated generate-compile-repair loop. Machine-generated
code is exactly the code you least want running with unbounded ambient
authority: the author is not a human who reviewed every syscall. A language whose
premise is "LLMs write this" should arguably have "the program declares what it
may touch" as a first-class property.

The existing [sandbox-setup.md](/docs/security/sandbox-setup/) shows the project
already relies on **external** OS sandboxing (`sandbox-exec` profiles on macOS,
`docker --network none --read-only` on Linux) to run corpus binaries safely.
That is the right tool for the *test harness*, but it is an operator-supplied,
per-invocation wrapper — not a property of a shipped toke program, not portable
into an ooke deployment, and not something an LLM-generated program can rely on
being present. The capability question is whether toke should also carry an
**in-language** model so safety does not depend on every deployer remembering to
wrap the binary.

## Decision

**Proposed — not yet decided.** Three options are laid out below with honest
trade-offs, followed by a recommendation. The owner selects A, B, or C (or a
phased path between them).

---

### Option A — Status quo + documentation only

Keep ambient authority. Fix the concrete injection/symlink/PATH defects from
120.11 and 120.2 as ordinary bug-fix stories (Epic 121), and **document** the
trust model clearly: "a compiled toke program runs with the full authority of
the invoking user; sandbox it externally (see sandbox-setup.md) if you run
untrusted code."

- **What it changes for programs:** nothing. No source changes, no manifest, no
  recompile-to-declare.
- **Cost:** low. Bug fixes only (argv-vector exec, `lstat` in `rmdir_r`,
  normalizing containment join, `O_NOFOLLOW`, dotenv key allowlist, PATH
  snapshotting). These are worth doing under *any* option.
- **Trade-off / honest downside:** the headline gap (AMB-01) remains **open**.
  There is still no way to run semi-trusted code, no per-request privilege drop,
  and no "secure by default" claim can be made. toke stays in the same category
  as C: safe only when the operator wraps it. For a language marketed for
  *machine-generated* code this is the weakest posture — it pushes 100% of the
  safety burden onto every downstream deployer, forever.
- **When this is the right call:** if toke's near-term audience is exclusively
  first-party code on trusted hosts and the roadmap cannot absorb a
  language/stdlib change this cycle.

### Option B — Opt-in capability manifest

Add an **optional** capability declaration (a manifest block or compiler flag,
e.g. a `[capabilities]` section in a project file or `--caps fs.read=/srv/www,net`).
When present, the compiler links a runtime **broker** that each std entry point
consults, and anything not declared is denied. When **absent**, the program
compiles and runs exactly as today (ambient).

- **What it changes for programs:** nothing *unless the author opts in*. Existing
  programs keep working untouched; security-conscious authors add a manifest and
  get enforcement.
- **Cost:** medium. Requires the broker layer (one gate per capability class:
  `fs.read`, `fs.write`, `process.spawn`, `env.write`, `net`), each stdlib sink
  routed through it, and a manifest parser + compiler wiring. No forced migration.
- **Trade-off / honest downside:** it is **fail-open by default** — safety is a
  property only of programs that opted in, which is precisely the population that
  needed it least. LLM-generated code will not emit a manifest unless prompted to,
  so the machine-generation audience — the one ADR-0001 centres — gets no default
  protection. It also creates a two-mode language (branded "capability-aware" vs
  not) and the usual opt-in-security trap: the default is still unsafe, so the
  ecosystem norm stays unsafe.
- **When this is the right call:** as a **transitional stepping stone** to C —
  ship the broker machinery opt-in first, prove it out on ooke and the website,
  then flip the default. This de-risks C's migration by building the mechanism
  before mandating it.

### Option C — Deny-by-default capabilities (Deno-style grants)

Make the model **deny-by-default**. A program has **no** filesystem, network,
environment-write, or process-spawn authority unless it is granted, either at
run time via flags (`--allow-read=/srv/www`, `--allow-net=api.example.com`,
`--allow-run=/usr/bin/convert`, `--allow-env`, `--allow-write=...`) or at
compile time via a manifest that the compiler bakes into the binary's required
grant set. Each std sink consults the broker; an undeclared/unauthorized call
returns a capability error (fail-closed), not a syscall. This is the Deno model,
adapted to an AOT binary.

- **What it changes for programs:** every program that touches fs/net/env/process
  must **declare** what it needs — in the manifest, on the command line, or both.
  Programs that only compute are unaffected. ooke and the toke-website must ship a
  manifest enumerating their real footprint (webroot read, listen socket, cert
  paths, DB socket).
- **Cost:** high, and **breaking**. Every existing program that does I/O needs a
  grant set or it fails closed on first fs/net/process call. Requires the broker,
  the manifest format, compiler baking, run-time flag parsing, *and* a migration
  pass over the corpus, the stdlib self-tests, ooke, and the website. It needs a
  new spec section and interacts with the build toolchain (the compiler itself
  would ideally run its own child-`clang` invocation under a declared grant, which
  also closes the 120.2 COM-01/COM-02 build-time surface).
- **Trade-off / honest upside:** this is the only option that lets toke honestly
  say **"secure by default"** and the only one that protects *machine-generated*
  code without the LLM having to know to ask. It makes least-privilege the path of
  least resistance, gives ooke real per-deployment confinement, and turns "can
  this dependency read `~/.ssh`?" into a checkable, declared fact. It aligns the
  security model with ADR-0001's machine-generation premise: the program declares
  its authority the same way it declares its types.
- **Trade-off / honest downside:** it breaks every I/O program until migrated;
  it adds friction to the generate-compile-repair loop (the loop must now also get
  the grant set right, though this is *mechanical* and diagnostic-driven, which
  suits toke's structured-diagnostic model from ADR-0001 §4); and a naive design
  can push authors toward blanket `--allow-all`, re-creating ambient authority
  with extra steps. The grant grammar must make narrow grants easy and broad ones
  visibly ugly.

---

## Recommendation

**Adopt Option C (deny-by-default capabilities) as the target end-state, reached
via a phased path that begins with Option B's mechanism.** Concretely:

1. **Now (Epic 121, independent of this ADR):** fix the concrete 120.11 / 120.2
   defects regardless of which option is chosen — argv-vector exec as the default
   and an `unsafe_shell` gate for the string form (AMB-02); absolute-path/allowlist
   `process.spawn` with a PATH snapshot instead of ambient `execvp` (AMB-03);
   dotenv key allow/deny-list refusing `LD_*`/`DYLD_*`/`PATH`/`IFS` (AMB-04);
   `lstat`-based `rmdir_r` (AMB-05); a normalizing containment join with
   prefix-check (AMB-06); `O_NOFOLLOW`/`openat` variants (AMB-07); and no raw
   integer-as-pointer `os.read`/`os.write` (AMB-08). These are pure hardening and
   should not wait for the capability decision.
2. **Next (phase 1 — build B's machinery):** implement the runtime **broker** and
   the capability classes (`fs.read`, `fs.write`, `net`, `env.write`,
   `process.spawn`) as an **opt-in** manifest, exactly as Option B describes.
   Migrate ooke and the toke-website to declare their real footprint as the first
   real consumers. This proves the model without breaking anyone.
3. **Then (phase 2 — flip the default):** once the broker is proven and the
   first-party apps carry manifests, **flip to deny-by-default** (Option C) behind
   a major-version bump, with a `--allow-all` escape hatch for migration and a
   compiler diagnostic (structured, per ADR-0001 §4) that names the exact missing
   grant on the first denied call. The generate-compile-repair loop then repairs
   missing grants the same way it repairs type errors.

**Reasoning.** toke's entire premise (ADR-0001) is that *machines* write this
code and run it in an automated loop. Ambient authority is the wrong default for
machine-generated code, and opt-in security (B, as an end-state) protects only the
authors who already knew to opt in — i.e. not the LLM. C is the only option
consistent with a "secure by default" claim, and toke is young enough (per the
project's "do it right, not workarounds" principle) to absorb one breaking change
now rather than carrying an ambient-authority legacy forever. Routing to C *via*
B's mechanism keeps the migration honest: the machinery is built and validated
opt-in before it is made mandatory, so the flip is a policy change, not a
rewrite. External OS sandboxing (sandbox-setup.md) remains the correct
belt-and-suspenders layer for running fully untrusted binaries and is
complementary to — not a replacement for — an in-language model.

**Migration cost (Option C, phase 2).** Every I/O-performing program needs a
grant set. For first-party code this is bounded and known: ooke (webroot read,
listen socket, TLS cert/key paths, SQLite/DB socket, any `process.spawn` it
actually uses) and the toke-website (static root, listen socket, cert paths). The
stdlib self-tests and the corpus harness need per-program manifests or a test-mode
`--allow-all`. Third-party/LLM-generated programs migrate by adding the grant the
diagnostic tells them they are missing — mechanical, not creative. The build
toolchain migration (compiler's own child-process/env use) is a bonus that closes
the 120.2 build-time injection surface.

**Impact on existing programs.**
- Under **A**: zero.
- Under **B**: zero unless an author opts in.
- Under **C**: every program that does fs/net/env-write/process I/O must declare
  grants or it fails closed; pure-computation programs are unaffected. This is a
  breaking change and must land behind a major-version bump with a migration
  window and the `--allow-all` escape hatch.

## Consequences

- **If C is chosen:** a new normative spec section for the capability model and
  manifest grammar; a runtime broker in the stdlib; compiler wiring to bake grant
  sets; a structured diagnostic for denied capabilities; and a corpus/first-party
  migration pass. toke can then make a defensible "secure by default" claim.
- **If B is chosen as an end-state:** the broker exists but the default stays
  ambient; the "secure by default" claim cannot be made, and the machine-generation
  audience is unprotected by default.
- **If A is chosen:** AMB-01 stays open and is documented as accepted risk; safety
  remains an operator responsibility via external sandboxing.
- **Regardless of option:** the concrete 120.11 / 120.2 defects are fixed in Epic
  121, and `docs/security/path-traversal-audit.md` should reference the new
  containment-join primitive (AMB-06).

## Alternatives considered

- **Rely solely on external OS sandboxing (sandbox-setup.md) as the answer.**
  Rejected as *the* answer: it is operator-supplied and per-invocation, absent by
  default, and cannot express per-request privilege drop inside a long-running ooke
  server. Retained as a complementary defence-in-depth layer.
- **Ship the capability model as accepted immediately.** Rejected for this ADR:
  the A/B/C choice is an owner decision with a real breaking-change and roadmap
  cost, so this ADR stays **Proposed** pending that call.
